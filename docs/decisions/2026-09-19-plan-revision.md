## 背景: 今日の実測が壊した前提

外部基準 (やねうら王 + Háo を depth 1 に制限、floodgate 序盤ブック 500 通り、各 100 局、SE ≈ 0.04) を
初めて立てた結果、それまでの前提が複数崩れた。

| 元の前提 | 実測 |
|---|---|
| 自己対戦 RL で強くなる | PPO 9,200 iter で **+0.01** (phase37 0.22 → ppo2 0.23、誤差内) |
| 文化リーグは強さにも寄与 | 0.10〜0.16 で**蒸留より下** |
| 感情 GRU の解凍は有望 | **有害** (0.110、対応あり符号検定 p=0.036、用量反応あり) |

そして**構造分析がこれを説明した** (パラメータ実測、解剖図 https://claude.ai/artifact/1BKp4Y4GWoxY6jF9Yn9g65):

| 部位 | パラメータ | 割合 |
|---|---|---|
| trunk (6層 Transformer) | 4,738,560 | **94.68%** |
| 会議 (proposal_embed) | 108,032 | 2.16% |
| 内面 (感情GRU + 性格 + 関係) | 4,654 | **0.09%** |
| attention バイアス (利き3値×8ヘッド + 関係8) | **32** | 0.0006% |

**trunk を動かさない施策は強さを動かさない** — 文化リーグが動かすのは θ_sp の 224 個、
感情 GRU の解凍が動かすのは 4,128 個。500 万個のモデルの強さが変わらないのは構造上の必然だった。

## 変更 1: Phase F (アーキテクチャ) を最後尾から前倒しする

**元の順序**: A 土台 → B 会議 → C 学習信号 → D 自己対戦 → E 内面 → **F アーキ (最後)**
**新しい順序**: A' 測定の完成 → B 会議 → **F' trunk の改良** → C' 教師蒸留の判断 → D' 自己対戦1本勝負 → E' 内面 (別目的)

**理由**: 強さを動かせるのが trunk (94.68%) だけだと実測で分かった以上、trunk を改変する Phase F は
「余力があれば」ではなく**本線**に置くべき。B (会議) は trunk を重み共有で再利用する仕組みなので、
「データを増やさず計算量で強くする」唯一の候補として先に置く。

**F' の中身 (安い順)**:
1. **attention バイアスの拡張** ← 最優先。現在は利き 3 値 (NO_EFFECT / ATTACKS_ENEMY / SUPPORTS_ALLY)
   × 8 ヘッドの **24 パラメータ**しかない。ピン・飛び利き・距離・同筋/同段などを加えるのは埋め込みを
   増やすだけで、再学習も warm start が効く。Chessformer (arXiv:2605.19091) は幾何的 attention バイアス
   (GAB) で LC0 に +100 Elo を出している
2. 持ち駒トークンの情報量 (現在は位置 ID 81/82 のみ。枚数・同種の何枚目かを持たせる)
3. モデルスケール d=384 / 8層 (8GB では限界近く、AMP で VRAM を空けてから。warm start 不可＝全再学習)

## 変更 2: Phase A (測定) を完成させてから次に進む

今日の物差しは**エンジン 1 種・深さ 1 段**しかない。今日 1 日で測定起因の誤判断が 3 回起きた
(アンカーすり替わり / 決定論による標本縮退 / ゲートが崩壊しか検知しない) ので、ここをケチらない。

**A' の中身 (半日)**:
1. **複数の強さで測る** — 対 Háo depth 1 / 2 / 4 (いずれも序盤ブック付き)。1 段だけだと
   「その深さに特化していないか」が分からない
2. **Bradley-Terry で Elo と信頼区間** — 現在は勝率の生値と手作業の符号検定。
   `select_final.py` に BT 実装があるので統合し、`scripts/eval_harness.py` として 1 コマンド 1 JSON にする
3. **強さ × 説明率の 2 軸を毎回記録** — アブレーション表で「A+D で説明率が急落 (69〜70%)」が
   見つかったように、強さだけ追うと解釈可能性が静かに死ぬ。ダッシュボードに両方を出す
4. **異なる棋譜の数を必ず併記** — 決定論による標本縮退の再発防止 (今日の第1弾は 100 局が実質 2 局だった)

## 保留 (今夜の結果で決める)

- **変更 3 (Phase D を 1 本の決定実験に圧縮)** — 自己対戦の路線を閉じるかどうか
- **変更 5 (規模の判断)** — 教師蒸留を桁で増やすか撤退するか。Ruoss et al. は 270M パラメータ・
  150 億データ点。本プロジェクトは 5M・180 万点で **1/54 と 1/8,000**
- **変更 6 (Phase E を強さの計画から分離)** — 内面は 0.09% しかないので「面白さ・解釈可能性」の
  目的に置き直し、外部基準では測らない

これらは 2026-09-19 夜の本走 (教師 vs 対照、各 20k 局) と E4c / Phase B の結果を見てから確定する。

## 運用上の教訓 (今日 2 回踏んだ)

**`pgrep -f <スクリプト名>` で他ジョブの生存を判定してはいけない。** 監視シェルのコマンド文字列に
同じ語が含まれると永久にマッチする。実際に夜間チェーンの待機条件がこれで解けず、GPU が遊んだ
(20:34〜20:38)。**GPU の占有判定は `nvidia-smi --query-compute-apps=pid` を使う**。
同根の罠として `pkill -f` の自己マッチ (自分のシェルを殺す) も今日 2 回起きている。
