## 何を決めたか

発表後に棋力を追求する場合、経路は **「推論時探索 + エンジン教師蒸留」の1本**に絞る。
探索を通した自己対戦RL (本物の AlphaZero) とモデルの大型化は、現機材 (RTX 3070 Ti 8GB・
WSL2・GPUジョブ1本ずつ) では回らないので**やらない**。

強さそのもので勝負する道ではなく、**駒粒度の解釈可能性を保ったままどこまで行けるかを示す**
ことを目的とする。探索は π と V を prior に使うラッパーで、駒トークン・欲求・性格・会議には
触れない (設計原則1「強さの経路と面白さの経路の分離」と整合)。

## 現在地 (2026-09-19)

- policy-only (argmax + τ)。**探索は未実装** (MCTS / Gumbel 系のコードは無い)
- 強さの数値は**すべて自己相対** (対 ppo2 勝率、はしごElo)。絶対棋力の物差しが無い
- 測定起因の事故が既に起きている: ADR 2026-08-31 追記3 (アンカーすり替わり・argmax診断の縮退で
  約4時間の学習を誤って破棄)。はしご評価は 1.5〜4 倍に水増しされる (2026-09-02 の教訓)
- `SelfPlayEnv` は毎回 `cshogi.Board()` (平手初期局面) から始めている。開始局面の多様性は τ=0.8 のみ

## 経路の判定

| 経路 | 判定 | 理由 |
|---|---|---|
| 推論時探索 (学習済み π, V の上に Gumbel-Top-k + Sequential Halving) | ○ | 学習不要。実装だけで実戦棋力が上がる |
| エンジン教師蒸留 (CPU で教師局面生成、GPU で蒸留) | ○ | 生成が CPU なので GPU と並行できる |
| 開始局面の多様化・詰み探索併用 | ○ | 小さく確実 |
| 探索を通した自己対戦RL | × | 1手32simで自己対戦が約30倍重い。3070 Ti 1枚では回らない |
| モデルの大型化 | △ | batch 24 が VRAM の安全ライン。余地がほぼ無い |
| 外部エンジンを PPO の対戦相手に入れる | × | CPU逐次で律速になる。強すぎる固定相手は報酬信号も消える |
| エントロピー係数の介入 | × | ADR 2026-08-31 で失敗と記録済み |

## やること (順序付き)

0. **詰み探索の併用** — `cshogi.Board.mate_move_in_1ply()` / `mate_move(ply)` (奇数手≥3) を指す直前に呼び、
   見つかれば無条件にそれを指す。実装10行・学習不要。**発表前でも入れられる唯一の項目**
   (実況では「詰みを発見したので議論を打ち切った」と出せる)
1. **推論時探索** — `DESIGN.md` §4c のまま。会議 R=2 の forward は重い (trunk 最終2層×3回) が
   prior の質が高い (46.16% vs R=0 の 28.66%) ので少数シミュレーションで成立させる設計を維持
2. **物差し** — USI アダプタ `scripts/usi_server.py` (新規1ファイル、既存コード変更なし) +
   ノード制限を固定した外部エンジン。**提案1〜3の効果が本物かを判定するため、先に立てる**
   - USI の `position` は毎回全手順を送る → `PieceIdTracker` / 感情 m / 関係 R を初手から再生する必要。
     直前手順との前方一致で差分だけ進める prefix キャッシュにする
   - 時刻合わせは `play_server.py` の `ModelEngine` と同一にする (ずれると Unity 対局と USI 対局で手が変わる)
   - `info string` に会議ログ (`CouncilRoundLog` + `TemplateNarrator`) と感情3軸を流す
   - 再利用: `export_model_jsonl.ModelRunner` / `build_action_map` / `sample_move`、cshogi の USI 変換
   - 不要: ponder / stop / go mate / multipv。option は Culture (combo) と Tau (spin) のみ
   - 探索なしエンジンをノード制限エンジンと比べる設計は「何と比べたいか」を先に決める
3. **エンジン教師蒸留**
   - value 教師: 最終結果 z (1局1ビット) をエンジン評価値 (全局面に密) に差し替え。cp → 勝率 → [-1,+1] で
     既存の c1·L_value にそのまま入る
   - soft target: `go multipv N` の上位N手を softmax(cp/T) で KL 蒸留 (one-hot CE は2番目の好手を罰する)
   - 教師局面生成は やねうら王 `gensfen` (learn ビルドが必要)。まず 1〜2M 局面で効果を確認してから拡大
   - 欲求ラベルは手順から自動生成されるので、エンジン棋譜もそのままパイプラインに乗る
4. **開始局面の多様化** — ADR 2026-08-31 の「(a) プール多様性」に対応。互角局面 (±200cp 程度) を
   数千通り作って自己対戦の入口にする (`gensfen` の random_move_minply/maxply/count が使える)
   - **ブックは SFEN ではなく手順 (moves) で持つ**: `PieceIdTracker.__init__` は持ち駒あり局面を
     `ValueError` で弾く (`piece_state.py:143-147`)。感情・関係も履歴依存なので、初手から再生する
   - `SelfPlayEnv` に開始手順を渡す引数を足す (50行程度)。USI の position 再生と構造を共有できる
5. **|g| 捨て駒検出の定量化** — `DESIGN.md` §8 の未実施項目。エンジン評価値で正解 (駒損するのに評価値が
   落ちない手) を機械生成し、`scripts/analyze_free_term.py` に precision/recall を足す。強さではなく発表向け

### 2026-09-19 学習なしの「最強構成」総当たり (対 ppo2.pt、各 100 局、τ_incumbent=0.1)

| 候補 | 勝率 | 引分 | 判定 |
|---|---|---|---|
| E2b culture4, τ=0.1 (旧既定) | 0.540 | 24 | 基準 |
| E2b culture1, τ=0.1 | 0.670 / 0.635 (シード B) | 36 / 39 | +13pt |
| **E2b culture1, τ=0 (argmax)** | **0.825 / 0.780 (B) / 0.720 (C)** | 15 / 22 / 24 | **+14〜15pt (同シード比)**、3 シードで再現 |
| E2b culture1, τ=0.1 + 1手詰 | 0.710 | 36 | +4pt (ノイズ範囲) |
| E2b culture1, τ=0 + 1手詰 (B) | 0.825 | 25 | argmax 単体 (B) 0.780 に +4.5pt、詰み 70 回 |
| 6 文化 logits 平均 (アンサンブル) | 0.555 | 41 | 効かない (推論 3.5 倍) |
| ppo2 スナップショット重み平均 t31-39 | 0.490 | 8 | 効かない |
| 同 t35-39 | 0.225 | 17 | **壊れる** (後半スナップは同じ谷にいない) |

決定: `scripts/play_server.py` の既定を **culture1 + τ=0 + 1手詰チェック ON** に変更
(`DEFAULT_CULTURE` / `DEFAULT_TAU` / `--no-mate-check`)。重み平均・アンサンブルは不採用。
測定スクリプトは scratchpad の strongest.py / verify_argmax.py、結果は
`checkpoints/strongest_eval.json` / `checkpoints/strongest_verify.json`。

注意: 温度 τ=0 は決定論なので、同じ相手には同じ棋譜になる。人間相手のデモで揺らぎが欲しければ `--tau 0.1`。
評価側 (incumbent) は常に τ=0.1 で指させているので、この数字は「こちらが決定論・相手が確率的」の条件。
