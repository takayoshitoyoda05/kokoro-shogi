# 技術報告: 駒ごとのエージェント分解による探索なし将棋 AI

**KokoroPolicy** — 5,000,823 パラメータ / 探索なし (1 手読み) / 外部基準 対 Háo depth 1 で勝率 0.230

2026-09-21

---

## 要旨

本報告は、将棋の 1 局面を **40 個の駒トークン**として符号化し、駒ごとに 6 軸の欲求・正値の性格重み・
自由項を持たせ、それらを**全駒共通の 1 本の softmax** で調停して指し手分布を作るモデル
**KokoroPolicy** を記述する。価値は駒ごとの価値 `V_i` を単調に混合して構成し、混合重み `α_i` を
「発言力」として外部へ公開する。推論時に木探索を一切行わない。

学習は floodgate 棋譜 155,992 局 (約 2,240 万局面) からの系列蒸留を主軸とし、欲求 6 軸の教師は
棋譜からルールベースで自動生成する (人手のアノテーションはゼロ)。これに自己対戦 PPO と
文化リーグ (PBT) を重ねた。

2026 年 9 月、初めて**外部エンジン (やねうら王 + Háo NNUE) を固定基準**として絶対的な強さを
測った結果、**蒸留のみのモデル (0.220) に対し、自己対戦 PPO 9,200 反復は +0.01、文化リーグは
−0.07〜−0.13、感情 GRU の解凍は用量依存で −0.18** であった。パラメータの 94.7% が共有 trunk に
あり、内面が 0.09% しかないという構造がこの結果をよく説明する。さらに trunk の epoch 追加も
4 回目で頭打ちとなり、train 一致率 47.3% に対し val 41.5%、その差が epoch ごとに拡大している
ことから、現在の律速は**容量ではなくデータ量**であると診断した。

## 1. 設計の前提

本プロジェクトの目的は二つある。**(a) 探索を使わずに将棋を指せるだけ強くすること**、
**(b) その指し手を駒ごとの動機として説明できること**。両立のために置いた設計原則が一つある。

> 面白さのための機能をすべて切っても、素の強い将棋 AI が残ること。

これを実装レベルで保証するために、内面に関する機構 (感情・関係性・個体性格・文化) はすべて
**零初期化された加算項**として挿入されている。機能フラグを false にすると素の駒トークン
Transformer と**数値的に完全に一致**する。新機能を既存チェックポイントに足しても、その瞬間の
性能は変わらない。

木探索を使わない方針は 2026-09-19 に確定した。推論時探索は強さには効くが、「駒たちが会議して
決める」という説明可能性の中核と噛み合わないためである。代わりに**推論時の反復 (会議ループ)** で
計算量を増やす方向を採った。

## 2. 局面の表現

### 2.1 駒トークン

盤 81 マスではなく**駒 40 枚**をトークンにする。各駒は 4 つの整数で表される。

| 配列 | 形 | 値域 | 意味 |
|---|---|---|---|
| `species` | (40,) int8 | 0–13 | FU KY KE GI KI KA HI OU / TO NY NK NG UM RY |
| `position` | (40,) int8 | 0–82 | 0–80 = 盤の 81 マス、**81 = 先手の駒台、82 = 後手の駒台** |
| `owner` | (40,) int8 | 0 / 1 | 0 = 先手、1 = 後手 |
| `promoted` | (40,) int8 | 0 / 1 | 成っているか |
| `mask` | (40,) bool | 常に 1 | 将棋では駒が盤から消えないため |
| `turn` | スカラー | 0 / 1 | 手番 |

並びは `piece_id` の辞書順に固定される。`piece_id` は `<駒種の文字><初期マス>_gen<世代>_<連番>`
の形で (例 `P77_gen0_0029` = 7七にいた歩)、**対局中いっさい変わらない**。

この設計の帰結として、**駒は捕獲されても消えない**。取られた駒は `position` が 81/82 になり
`owner` が反転するだけで、同じトークンとして生き続ける。打ち直されれば盤上に戻る。「駒が敵に
転生する」という表現はこの実装に由来する。副次的な利点として、**トークン数が常に 40 で固定**され、
可変長系列を扱う必要がない。

> **位置は 83 通りの ID を引くだけである。** 座標 (筋・段) も距離も方向も与えていない。
> 「5五と 5六が隣である」ことすら、モデルは重みから学習で獲得している。

### 2.2 補助行列

トークンとは別に、局面ごとにルールで計算して attention と損失へ渡すものが三つある。

| 名前 | 形 | 値 | 用途 |
|---|---|---|---|
| `effect` (利き) | (40, 40) | 0 / 1 / 2 | attention バイアス。0 = 関係なし、1 = i が敵 j に利く、2 = i が味方 j に紐 |
| `relation` (絆) | (40, 40) | [0, 1] 実数 | 紐関係の EMA 時間積分。attention バイアス |
| `legal` (合法手) | (40, 81, 2) | bool | 非合法手を −10⁹ で潰す |

`effect` が表せるのは「駒 i と駒 j の間に利きがあるか」だけである。**空きマスへの利き (玉の逃げ道、
打ち場所)、飛角香の線、遮り、距離・方向は表現できない。** これは §8 で再訪する。

## 3. アーキテクチャ

### 3.1 全体

```
局面 → 駒トークン40 → trunk(6層) → 欲求・性格・自由項 → 会議ループ(R回) → 全駒softmax → 指し手
                         ↘ 駒ごとの価値 V_i → 単調混合 → V(s)
```

| ブロック | パラメータ | 割合 |
|---|---:|---:|
| trunk (6 層 Transformer) | 4,774,176 | 95.47% |
| proposal_embed (会議の提案埋め込み) | 108,032 | 2.16% |
| mixing (価値の単調混合) | 76,586 | 1.53% |
| desire_head (欲求 6 軸) | 20,838 | 0.42% |
| free_term_head (自由項) | 20,673 | 0.41% |
| personality (性格) | 518 | 0.01% |
| **合計** (+ モデル外の感情 GRU 4,128) | **5,000,823** | 100% |

数字は `mood` / `relations` / `council` を有効にした構成のもの。`individual` / `loyalty` も
有効にすると 5,005,050 になる。

### 3.2 共有 trunk

d_model = 256、6 層、8 ヘッド (head_dim 32)、FFN 中間 1024、**Pre-LN**。1 層 789,760 パラメータ。

```
x ← x + Attn(LN₁(x))     attention 263,168 (QKV 一括 256→768 + 出力射影 256→256)
x ← x + FFN(LN₂(x))      FFN 525,568 (256→1024→GELU→256) = 1 層の 66.5%
```

attention が**駒どうし**を混ぜ、FFN が**1 駒の中の 256 次元**を変換する (position-wise)。
残差接続により全 6 層で 256 次元が固定される。**層は直列、ヘッドと 40 トークンは並列**である。

`nn.TransformerEncoderLayer` は使わず自前実装している。PyTorch のこの層は `norm_first=True` の
とき**非ゼロの float マスクを渡すと出力が NaN になる** (bool と誤解釈され全キーが塞がれる)。
本設計は加算バイアスを多用するため致命的であり、回帰テスト
`test_nonzero_attention_bias_stays_finite` で固定している。

### 3.3 attention バイアス — 将棋の知識は 32 パラメータ

```
e_ij = (q_i · k_jᵀ)/√32  +  B_利き[effect_ij][h]  +  w_r[h] · r_ij
```

`B_利き` は `nn.Embedding(3, 8)` (3 種の利き × 8 ヘッド = **24**)、`w_r` はヘッドごとのスカラー
(**8**)。**合計 32 個**で将棋の駒の関係を表す。どちらも零初期化。

学習済み `ppo2.pt` を開くと、零から始まったヘッドがはっきり分化している。

| ヘッド | 攻撃寄り | 紐寄り | 絆 r_ij | 読み取れる役割 |
|---|---:|---:|---:|---|
| head 0 | +3.14 | +1.61 | +0.34 | 取り合いを見る |
| head 5 | +1.76 | +2.99 | +0.02 | 守りの構造を見る |
| head 6 | −2.06 | −1.15 | −0.10 | 利きのない駒どうしを見る |
| head 7 | −0.36 | −0.13 | +0.82 | 長期の絆だけを見る |
| head 1–4 | −1.24 〜 −0.10 | −1.71 〜 −0.35 | −0.28 〜 +0.52 | 利きを避ける / 中立 |

中盤局面で測ると、head 0 のバイアス (+3.14) は**内容ベースの attention 論理値の標準偏差の 4.6 倍**に
達する。ただし利き関係のあるペアは全体の 3.1% (50/1600) しかないため、注目分布の実際の変化は
全変動距離で平均 0.052 (head 5 で 0.240) にとどまる。**32 個は「少数の重要なペアだけを、非常に
強く」動かしている。**

なお、この 32 個は**全 6 層で共有**されている。層ごとに別の値を持てば、浅い層は局所的な取り合い、
深い層は大局的な構造、といった分業が可能になるが、現状はできない。

### 3.4 方策 — 駒ごとの分解と全駒 softmax

```
s_i(a) = ⟨w_i, d_i(a)⟩ + g_i(a)                       駒 i が手 a を指したいスコア
w_i    = softplus(W_w[θ_sp ‖ θ_ind ‖ m_i]) > 0        性格重み (正値制約が解釈可能性の要)
d_i(a) ∈ [0,1]⁶                                       欲求 6 軸
g_i(a)                                                自由項。欲求で説明できない残差

π(a|s) = exp(s_i,a / τ) / Σ_j Σ_a' exp(s_j,a' / τ)    40×81×2 = 6,480 を 1 本の softmax
```

**駒ごとに正規化しない**のが要点である。分母を全駒で共有することで、「駒 A の主張が強くなれば
駒 B の確率が下がる」という競合が 1 つの微分可能な式になる。駒ごとに softmax すると「各駒の中での
最善手」しか得られず、調停が表現できない。

**計算の工夫**: 6,480 通りの入力を素直に作ると 1 局面あたり 6480×321 になる。第 1 層が線形である
ことを使い、駒ごとの項 `(B,N,1,32)` と手ごとの項 `(162,32)` に分解してブロードキャストで足す。
中間テンソルは `(B,N,162,32)` で済む。

自由項 `g` には L2 罰則 (λ_g = 0.01) がかかる。小さく保たれているにもかかわらず大きい `|g|` は
「本能に反した大局的判断」= **捨て駒**の検出器になる。λ_g を 0 → 0.01 にすると欲求説明率が
0.19 → 0.40 に跳ね、一致率の代償は 0.5pt であった。

### 3.5 価値 — 単調混合と発言力

```
V(s) = tanh( Σ_i α_i V_i + MLP_b(h̄) ),   α_i ≥ 0 かつ Σα_i = 1
```

QMIX / Qatten 流の単調混合である。`α_i = |W_hyp h̄|_i` は状態依存の非負重みで、**∂V/∂V_i ≥ 0**
(IGM 単調性) が保たれる。この `α_i` が「駒 i の価値判断が今の形勢にどれだけ効いているか」=
**発言力**で、Unity へ `pieces[].alpha` として送られ、駒の光り方になる。

> **V_i は出力に存在するが、どの損失にも使われていない。** 混合後の V だけが勝敗 z と比較される。
> 局面あたり 40 個の教師をかけられる場所が空いており、これが §8.3 で述べる次の実験の入口になっている。

### 3.6 会議ループ — 重み共有による推論時反復

```
for r in 1..R:
    上位 k=8 の提案 (駒, 手, bid) を選ぶ
    提案を 8 トークンに埋め込む                  proposal_embed 108,032
    [駒40 ; 提案8] に trunk の末尾 2 層を再適用   新規パラメータなし
    スコアを計算し直す
```

新しい層は作らない。既存の 5 層目と 6 層目を使い回すため、**ラウンド数 R は学習後に自由に
変えられる**。既定 R = 2 で実効深さ 10 段になる。提案トークンは全駒から参照でき、利き・関係
バイアスは駒×駒の左上 40×40 ブロックにだけ載る。

**random loop sampling** (2026-09-19 導入、STARS 由来): 学習時に R を集合 `{1,2,3,4}` から一様に
引く。固定 R で学習すると推論時に R を変えた際に崩れるためである。効果は §6.4 に示す。

### 3.7 手をまたぐ状態

| 状態 | パラメータ | 更新則 |
|---|---:|---|
| 感情 m_i (32 次元) | 4,128 | 9 次元イベントで GRU 更新。全駒で共有、駒ごとに別の隠れ状態 |
| 関係 r_ij | 8 | R ← 0.9R + 0.1·bond (EMA。相互紐 10 手で 0.65) |
| 個体性格 θ_ind (16 次元) | 16 / 駒 | 対局を跨いで SQLite に永続化 |

イベント特徴 9 次元は `moved` / `captured` / `was_captured` / `promoted` / `ally_lost` /
`enemy_lost` / `threatened` / `king_in_check` / `material_swing`。`ally_lost` と `enemy_lost` は
**L1 距離で減衰** (2 マスで 1/e) して全駒に伝わる。事件現場に近い駒ほど強く動揺する。

## 4. 学習

### 4.1 データパイプライン

```
floodgate CSA → parse_csa → accept_game → encode_game → シャード(.npz) → SequenceDataset → 学習
```

| 段階 | 内容 |
|---|---|
| 取得 | floodgate 年次アーカイブ。2026-09-21 時点で 2008–2026 の 19 年 = 1,883,113 局 |
| 採否 | 両者レート ≥ 3000 / 手数 50–400 / 中断・不正手を除外 / 平手初期局面から始まること |
| 符号化 | 1 局を局面ごとに分解し、トークン 4 列 + 指し手 + 勝敗 + 欲求ラベルを積む |
| 規模 | **155,992 局 ≈ 2,240 万局面** (226 シャード、11GB) |

シャードは**局の境界で切る**。感情 GRU の学習には 1 局を通した系列が要るためである。学習時は
`SequenceDataset` が `move` 列から cshogi で局を再生し、利き行列・合法手マスク・イベント特徴を
正確に復元する (これらはシャードに保存していない)。

> **採否条件のうち「レート ≥ 3000」で全体の 53.3% を捨てている。** 2026-09-21 の標本調査
> (6,000 局) で実測。この足切りは §8.2 で見直す。

### 4.2 欲求ラベルの自動生成

補助損失の教師 y は棋譜から**ルールベースで生成**する。人手のアノテーションはゼロである。
先読み幅 k = 4 手。

| 軸 | 判定 | 型 |
|---|---|---|
| survive | k 手後に盤上にいるか | 0/1 |
| attack | k 手以内にこの駒が捕獲または王手をかけたか | 0/1 |
| promote | k 手以内にこの駒が成ったか | 0/1 |
| defend | 今の局面で紐を付けている味方の数 (玉は重み 2) を正規化 | [0,1] 連続 |
| advance | k 手後に敵陣側へ進んでいるか | 0/1 |
| redeploy | 持ち駒のとき、k 手以内に打たれたか | 0/1 |

ラベルは局面 t における駒 i の性質で、手には依存しない。一方 `d_i(a)` は手ごとに出るので、
損失では**実際に指された手 a_t の (移動先, 成り) を全駒に当てて**突き合わせる。

### 4.3 統一損失

```
L = L_policy + c₁·L_value + c₂·L_desire + λ_g·L_g − c₃·H(π)
                [ + c_soft·L_teacher ]    エンジン教師がある局面のみ
                [ + λ_f·L_fate ]          2026-09-21 追加、検証中
```

| 項 | 定義 | 係数 |
|---|---|---:|
| L_policy | 指された手の交差エントロピー (RL では PPO クリップ損失) | 1 (固定) |
| L_value | (V − z)²。z は手番側視点の勝敗 ∈ {+1, 0, −1} | c₁ = 1.0 |
| L_desire | 6 軸の BCE。有効トークンで平均 | c₂ = 0.5 |
| L_g | 合法手だけで取る g の L2 | λ_g = 0.01 |
| H(π) | エントロピーボーナス (RL のみ) | c₃ = 0.01 |

c₃ は 2026-08-31 に 0.03 / 0.02 への引き上げを試したが、いずれも argmax 診断が知識侵食と
判定したため原値に戻した。

評価指標として**欲求説明率** `E⟨w,d⟩² / E s²` を毎エポック記録する。大きいほど手の選択が欲求で
説明でき、小さいほど自由項 (大局観) に頼っている。`s = ⟨w,d⟩ + g` なので g が `⟨w,d⟩` と逆相関
すると 100% を超えうる (比であって割合ではない)。

### 4.4 系列蒸留 (主軸)

感情 GRU は 1 局を通して回す必要があるため、局面単位ではなく**局単位**で学習する。

```
for バッチ (24 局):
    m ← 0, R ← 0
    for t in 0..T-1:                       1 手ずつ、局の頭から
        m ← GRU(event_t, m)                感情を更新
        R ← 0.9R + 0.1·bond_t              関係を更新
        out ← policy.forward(step_t, m, R)
        loss_t ← 統一損失
        窓に積む。16 手ごとに backward → step → 窓を空け、m を detach
```

| 設定 | 値 |
|---|---|
| 最適化 | AdamW、lr 2e-4、weight decay 1e-2、勾配クリップ 1.0 |
| バッチ | 24 局 / TBPTT 16 手 |
| 混合精度 | bf16 autocast (`--amp`)。損失は fp32 で計算 |
| 検証 | 32 局。数値の比較可能性のため常に fp32 |
| 1 epoch | 155,992 局で **約 13 時間** (実測 46,598 秒) |

実装上の注意: 1 手ごとに `float()` で GPU 同期すると、それだけで CPU を 1 コア食い潰す。そのため
損失はテンソルのまま加算集計し、バッチ末尾で一度だけ同期する (`compute_loss_tensors` が本体から
分離されている理由)。

### 4.5 自己対戦 PPO

疎報酬 r_T = z、GAE (γ = 1, λ = 0.95)、PPO クリップ ε = 0.2。将棋は手番が交互の零和なので、
価値と advantage は**手番側視点**で持ち、後続手の値を符号反転して伝播する (negamax 流)。

```
δ_t = r_t + γ·(−V(s_{t+1})) − V(s_t)
Â_t = δ_t + γλ·(−Â_{t+1})
```

| 設定 | 値 |
|---|---|
| 収集 | 16 局 / 反復、温度 τ = 0.8 (探索)、最大 180 手 |
| 更新 | 2 epoch、ミニバッチ 256、lr 1e-5 |
| 相手 | 過去のスナップショット最大 5 個のプール |
| 感情 GRU | **既定で凍結**。観測の一部として扱う |

L_desire の教師は自己対戦の棋譜からその場で生成する (蒸留と同じ規則)。打ち切り局は引き分け
(z = 0) とする。

### 4.6 文化リーグ (PBT)

文化 k = 駒種性格セット Φ_k = {θ_sp} + ハイパー (τ, λ_g)_k。**trunk とヘッドは全文化で共有**し
(AlphaStar リーグの共有バックボーンに相当)、文化ごとに Φ_k を差し替えて自己対戦 PPO を回す。
リーグ節ごとに総当たりで勝率を測り、下位を淘汰して Φ_k* + N(0, σ²) で置き換える。

進化するのは θ_sp の **14 × 16 = 224 個**だけである。この数字は §7.2 の結果を理解する鍵になる。

### 4.7 実際の系譜

```
phase37_e2 → phase37_e3 → ppo2 → { E1..E7, E2b(文化リーグ), E4系(GRU解凍), b系(会議), main系(教師蒸留) }
   0.110        0.220      0.230                0.10–0.16     0.05–0.175    0.165–0.20   0.16–0.18
```

すべての系列が `phase37_e3` (蒸留 3 epoch) を起点にしている。2026-09-21 に 4 epoch 目
(`phase37_e4`) を追加したが 0.200 で、e3 との対応あり符号検定は p = 0.875 であった (§7.5)。

## 5. 推論

### 5.1 持ち回る状態

推論は局面の関数ではない。`Position` オブジェクトが手順に沿って
**tracker (駒の同一性)・感情 m・関係 R・利き行列**を保つ。

```
初期化:   m ← 0, R ← 0, tracker ← PieceIdTracker(board)
1 手ごと: board.push(move) → tracker.apply_move → event 計算
          m ← GRU(event, m),  R ← 0.9R + 0.1·bond,  effect ← piece_effect_matrix
```

> **持ち駒のある局面から開始すると駒の同一性を復元できない。** 「この持ち駒の歩が元どの歩だったか」は
> 盤面からは決まらないためである。USI で `position sfen` に持ち駒が含まれる場合、tracker を諦め、
> **感情・関係・会議ログを持たない「記憶なし」モード**で指す (警告を出す)。

### 5.2 指し手の選択

```
1. 1 手詰チェック (board.mate_move_in_1ply) → あればそれを指す
2. forward → logits (6,480 次元)、非合法手は −10⁹
3. τ = 0 なら argmax、τ > 0 なら softmax(logits/τ) から多項サンプル
4. index → (駒トークン, 移動先, 成り) → action_map で cshogi の move へ
```

既定は **τ = 0 (argmax) + 1 手詰チェックあり**。1 手詰チェックを入れているのは、探索なしモデルが
単純な詰みを逃すためである。`action_map` は合法手を走査して逆引き表を作る (打ちは piece_id 最小の
持ち駒トークンに割り当てる規約)。

> **argmax と決定論エンジンの組み合わせは同じ棋譜を量産する。** 2026-09-19 の初回測定では
> 50 局中 49 局が同一棋譜になり、勝率 0.48 という誤った値を得た。現在は floodgate の序盤 500 種から
> 開始局面を配り、**異なる棋譜の数を必ず併記**している。

### 5.3 計算量

| 項目 | 値 |
|---|---|
| 1 手あたりの forward | **1 回** (木探索なし) |
| 実効深さ | 6 層 + 2 層 × R。既定 R = 2 で 10 段 |
| R の可変性 | 重み共有なので学習後に変更可。R = 1〜6 を実測済み |
| 実測速度 | 100 局 (平均 130 手) を CPU 2 スレッドで 40〜55 秒 |

### 5.4 提供形態

| 入口 | 用途 |
|---|---|
| `scripts/play_server.py` | WebSocket + JSONL。Unity クライアント向け |
| `scripts/usi_server.py` | USI エンジンとして公開。将棋所などから接続できる |
| `scripts/eval_vs_engine.py` | 外部エンジンとの対戦で絶対強度を測る (§6.2) |
| `scripts/eval_vs_model.py` | 凍結アンカーとの対戦で相対強度を測る (§8.4) |

Unity へは schema 1.1 の JSONL を送る。1 手ごとに 40 駒それぞれの `mood`
(fear/aggression/valence)・`desire` 6 軸・`alpha` (発言力)・`relations` と、会議の議事録
(ラウンドごとの上位提案と bid)、そして自然言語のナレーションが含まれる。契約の正本は
[`docs/INTERFACE.md`](./INTERFACE.md)。

## 6. 評価

### 6.1 2026-09-19 以前の指標とその限界

それまでの強さの数字は**すべて自己相対**であった (対 ppo2 勝率、はしご Elo、リーグ内総当たり)。
系列の外での強さは一度も測られていなかった。

### 6.2 外部基準の構築

| 要素 | 設定 |
|---|---|

| 報告 | 勝率に加え**先後別**と**異なる棋譜の数**を必ず併記 |
| 比較 | 序盤と手番が揃うので、モデル間は**対応あり符号検定**で比較する |

### 6.3 主要な結果

| モデル | 由来 | 対 Háo d1 |
|---|---|---:|
| teach2023_50k | エンジン教師蒸留 5 万局 | 0.245 |
| **ppo2** | phase37_e3 + PPO 9,200 反復 | **0.230** |

深さを変えた掃引 (depth 1 / 2 / 4) では順位がおおむね保たれた (ppo2 0.230 / 0.130 / 0.030、

## 7. 何が効かなかったか

否定的結果も同じ重みで記録する。以下はすべて外部基準による実測である。

### 7.1 自己対戦 PPO — +0.01

9,200 反復を回して phase37_e3 の 0.220 が ppo2 の 0.230 になった。自己相対では明確に強く
なっていた (対蒸留勝率 0.71) が、外部では誤差内である。**自己対戦の勝率は系列内でしか意味を
持たない。**

### 7.2 文化リーグ — −0.07〜−0.13

全条件で蒸留以下であった。進化させているのが θ_sp の 224 個だけであることを考えれば、500 万個の
モデルの強さが動かないのは当然とも言える。分化の研究としては維持するが、**強さの手段としては
閉じる**。

### 7.3 感情 GRU の解凍 — 用量依存で有害

2 因子 (学習率と anchor 強度) を分離する実験を行った。

| 条件 | gru-lr | anchor | Δgru @iter100 | 対 Háo |
|---|---:|---:|---:|---:|
| ppo2 (解凍なし) | — | — | — | 0.230 |
| E4 | 1e-5 | 1.0 | 0.091 | 0.175 |
| E4c | 1e-4 | 1.0 | 0.455 | **0.050** |
| E4b | 1e-4 | 0.1 | 0.500 | 0.110 |

拡散量の **92% が学習率だけで説明でき**、anchor はほとんど効いていない。そして**GRU を動かすほど
外部強さが下がる関係が 4 点で一貫**している。設定の問題ではなく路線そのものが有害である。
「感情を強化学習で育てる」は**閉じる**。

### 7.4 エンジン教師蒸留 — 検出できず

USI の MultiPV で局面ごとの指し手分布と評価値を取り (180 万局面)、SFEN をキーにシャードへ結合して
soft target と value target に加えた。

| 規模 | 教師あり | 対照 (`--no-teacher`) | 検定 |
|---|---:|---:|---|
| パイロット 4,000 局 | 0.205 | 0.205 | 完全同値 |
| 本走 20,000 局・全 226 シャード | 0.180 | 0.160 | 13 勝 11 敗 76 分、**p = 0.84** |

規模を 5 倍にしても効果が出ない。教師データ 180 万局面は Ruoss らの 150 億データ点の **1/8,000**
である。桁を上げるには CPU 数週間とモデル拡大が要るため、いったん棚上げする。

### 7.5 trunk の epoch 追加 — 4 回目で頭打ち

e2 → e3 で外部勝率が 0.110 → 0.220 と跳ねていた (対応あり 19 勝 8 敗、p = 0.052) ため、
「trunk の学習量がまだ伸びている」という仮説で 4 epoch 目を回した。

| | train 一致率 | val 一致率 | 差 | 対 Háo |
|---|---:|---:|---:|---:|
| e2 | 45.36% | 40.91% | 4.45pt | 0.110 |
| e3 | 46.61% | 41.28% | 5.33pt | 0.220 |
| e4 | 47.34% | 41.48% | **5.86pt** | 0.200 |

e3 → e4 は 19 勝 21 敗、**p = 0.875**。仮説は棄却された。e3 / e4 / ppo2 が 0.20〜0.23 に固まって
いるのに対し e2 だけが 0.110 であることから、「e3 で跳ねた」ではなく「**e2 が谷だった**」と読むのが
自然である (e1 の重みは 8/31 に上書きされ失われており、確認できない)。

## 8. 診断と今後

### 8.1 律速はデータ量である

§7.5 の表が鍵である。**train 一致率は毎 epoch 上がり続けている (45.4 → 47.3%) のに、val はほぼ
止まっており (40.9 → 41.5%)、差は epoch ごとに開いている** (4.45 → 5.33 → 5.86pt)。過学習の
教科書的な形である。

容量が足りないなら train も頭打ちになるはずだが、train はまだ伸びている。したがって**モデル拡大は
逆効果**であり、優先すべきはデータ量である。

補強証拠として、QK 回路の実効ランク (特異値エネルギーの 90% に要する本数、上限 32) は層 0 で 5.8、
層 4 で 17.2 と**32 次元を使い切っていない**。複雑な関係を学ぶだけのデータがない、と読むのが自然で
ある。

### 8.2 実施中の対策

| 施策 | 内容 | 状態 |
|---|---|---|
| 年の拡大 | floodgate 2008–2026 の 19 年を取得 (360,865 → **1,883,113 局**) | 完了 |
| レート線形重み | 足切り 3000 を 2000 へ緩め、w(e) = clip((e−2000)/2000, 0.05, 1) で重み付け (強さの比 20:1) | 実装済み |
| シャード再生成 | 2015–2026 の 12 年、上限 50 万局 (現行の 3.2 倍) | 生成中 |

2014 年以前は floodgate が CSA にレートを書いておらず (標本調査でレート既知 0%)、重み付けが
できないため対象から外した。また 188 万件中 8,523 件 (0.45%) に改行落ちで指し手がコメント行に
連結した棋譜があり、**cshogi のパーサが SIGSEGV で落ちる**。Python では捕捉できないため、渡す前に
「T 行は必ず指し手行の直後」という構造検査で弾いている。

### 8.3 次に試すこと

**(a) 駒の一生を教師にする。** `V_i` がどの損失にも使われていない (§3.5) ことを利用し、棋譜から
無料で取れる「運命」を直接の教師にする。

```
f_i(t) = −γ^k        k 手後に取られる
       = +b·γ^k      k 手後に成る
       = +c·γ^(T−t)  終局まで生き残る

L_fate = λ_f Σ_i mask_i (V_i − f_i)²
```

局面あたり 40 個、全局面に付く (教師蒸留が 8% の局面にしか付かなかったのと対照的)。さらに、
**捕獲で所有者が反転する瞬間に価値は消えず移転する**という保存則
`L_rebirth = λ_r Σ (V_i(t+1) − κ_species·V_i(t−1))²` を課す。κ は学習する移転係数である。
持ち駒の価値は将棋で最も評価が難しい量で、これを盤上の価値と学習した換算則で結ぶ。

**(b) 幾何を与える。** 3 値 × 8 ヘッドの利きバイアス (§3.3) を、線・遮り・距離・方向の相対バイアスに
置き換える。さらに先では**マストークン 81 個**を追加し、利きを本来の「駒 → マス」の関係として表す。
ただしチェスの研究では**ヘッドが駒種の動き方に自発的に特化する**ことが観察されており、幾何は
学習で獲得できる。焼き込みは「能力の追加」ではなく「容量の節約」として効くかどうかの賭けである。

**(c) 値損失を WDL 化する。** 現在の value 損失は素の MSE である。Czech らはチェスで**入力表現と
値損失 (MSE → WDL 交差エントロピー + 残り手数) だけで +180 Elo** を得ており、同論文で Vision
Transformer への置換は +30 Elo にとどまっている。内訳は入力表現 +97 Elo、値損失 +33 Elo。

### 8.4 測定の未解決問題

全モデルが勝率 0.02〜0.23 に潰れており、100 局でも勝敗が動く局が 10〜30 しかなく、差を検出しにくい。
`--engine-nodes` で相手を弱めて 0.5 付近に合わせようとしたが、**nodes = 1 でも depth 1 と同じ
0.230** で、探索量では相手を弱められなかった。律速は探索深さではなく Háo の評価関数そのもので
ある。

当面は**凍結アンカー** (`phase37_e3` を固定相手にモデル同士で対戦) との併記で感度を確保する。
絶対値のまま感度を上げるには評価関数を弱める必要があり、未着手である。

### 8.5 方法論の教訓

- **小さい勝率差を読み過ぎない。** 2026-09-19〜21 の 3 日間で 4 回誤った (決定論による標本縮退、
  ゲート通過の誤読、teach50k、e2→e3 の外挿)。必ず対応あり検定を通してから述べる。
- **ゲートは崩壊を検出するが有効性は検出しない。** E4 は自動ゲートを通過したが外部では有害だった。
- **実行中ジョブが依存するファイルを git stash しない。** 評価が無言で失敗し、原因究明に時間を要した。
- **損失専用のパラメータをモデルの state_dict に足さない。** 旧チェックポイントの strict 読み込みが
  全て壊れる。
- **学習の起動コマンドをログに残す。** phase37_e3 の lr が記録されておらず、再現が不完全である。
