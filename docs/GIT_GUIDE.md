# Git運用ガイド (初学者向け完全版)

> 対象: Gitをほぼ使ったことがない人を含むチーム全員。
> このプロジェクトでのGitの使い方を、最初の設定から毎日の手順、
> トラブル対処まで全部書く。**困ったらまずこの文書を検索**。
> 構成やフォルダの意味は `docs/REPO_STRUCTURE.md` を参照。

---

## 0. Gitの超基本 (3分で読める)

- **Git** = ファイルの変更履歴を記録する道具。「誰がいつ何を変えたか」が全部残り、
  いつでも過去に戻れる
- **GitHub** = その履歴をチームで共有する置き場 (クラウド)
- **コミット** = 「ここまでの変更をひとまとまりで記録」というセーブポイント
- **ブランチ** = 作業用の分身世界。`main` (本流) を汚さずに作業し、
  完成したら合流させる
- **Pull Request (PR)** = 「私のブランチをmainに合流させてください」という申請。
  合流前に他の人が内容を確認できる

このチームの鉄則は1つだけ: **mainには直接pushしない。作業は必ずブランチ → PR**。

## 1. 最初の1回だけやること (環境構築)

### 1.1 Gitのインストール
- Windows: https://git-scm.com/ からダウンロード → インストールは全部デフォルトでOK
- 確認: ターミナル (PowerShell) で `git --version` → バージョンが出ればOK

### 1.2 自分の名前とメールを登録 (コミットに記録される)
```bash
git config --global user.name "自分の名前 (GitHubのユーザー名でOK)"
git config --global user.email "GitHubに登録したメールアドレス"
```

### 1.3 Git LFS (大きいファイル用の拡張) — ★絶対に忘れない
```bash
git lfs install
```
**cloneより前に必ず実行。** 忘れると3Dモデル (FBX) が「数行のテキスト
(ポインタファイル)」としてダウンロードされ、Unityで開けない事故になる
(このチームの事故ランキング第1位候補)。

### 1.4 リポジトリを手元に持ってくる (clone)
```bash
cd 作業したいフォルダ
git clone https://github.com/takayoshitoyoda05/kokoro-shogi.git
cd kokoro-shogi
```
※ 初回はGitHubのログインを求められる。ブラウザ認証に従えばOK。

### 1.5 GUIを使いたい人へ (任意・推奨)
コマンドが怖い人は **GitHub Desktop** (無料) を入れてよい。
この文書のコマンドは全部GitHub Desktopのボタン操作でも可能
(clone = File→Clone / ブランチ作成 = Current Branchメニュー /
コミット = 左下のフォーム / push = 上部のPushボタン)。
**ただしLFSのinstall (1.3) だけはコマンドで先にやること。**

## 2. 毎日の作業の流れ (これが本体)

作業を始めるたびに、この順番を守る。

### STEP 1: 最新を取り込む
```bash
git switch main          # mainブランチに移動
git pull                 # GitHubの最新を取り込む
```
※ **Unityを触る人は、pullの前にUnityを閉じる** (開いたままpullすると壊れることがある)

### STEP 2: 作業ブランチを作る
```bash
git switch -c feature/やること名
# 例: git switch -c feature/replay-v0
# 例: git switch -c feature/koma-fu-model
```
命名は `feature/英数字とハイフン`。日本語は使わない。

### STEP 3: 作業する
ファイルを編集・作成する。**キリのいいところでこまめにコミット** (1日1回は最低限):
```bash
git add -A                        # 変更を全部ステージに載せる
git commit -m "駒の移動アニメを追加"   # 日本語一行でOK。「何をしたか」を書く
```
コミットメッセージのコツ: 「修正」「更新」だけはNG。「歩のシェイプキー名を
naming.mdに合わせて修正」のように、後から見て分かる粒度で。

### STEP 4: GitHubに上げる (push)
```bash
git push -u origin feature/やること名   # 初回
git push                              # 2回目以降
```
**1日の終わりに必ずpush** (PCが壊れても作業が残る + 進捗が見える)。

### STEP 5: Pull Requestを出す
1. GitHubのリポジトリページを開くと「Compare & pull request」の緑ボタンが
   出ているので押す (出ていなければ Pull requests タブ → New pull request)
2. タイトル: ブランチでやったことを一行
3. 本文に3つ書く: **何を / なぜ / 確認方法** (例: 「Replayシーンを再生して
   駒が動けばOK」)
4. Create pull request

### STEP 6: マージ
- マージ担当 (Python側=Taka、Unity/Blender側=U1) が内容を見て
  **Merge pull request** を押す
- マージされたら自分の手元を掃除:
```bash
git switch main
git pull
git branch -d feature/やること名   # 使い終わったブランチを消す
```

これで1サイクル完了。次の作業はまたSTEP 1から。

## 3. このプロジェクト特有のルール

| ルール | 理由 |
|---|---|
| mainに直接pushしない (必ずPR) | 壊れたコードがmainに入るとチーム全員が止まる |
| 自分の担当フォルダの外を触るときはDiscordで一言 | コンフリクト (§5.1) 防止 |
| Unityのシーン (.unity) は担当者以外編集しない | シーンのマージはほぼ不可能 |
| 同じPrefabを触るときは事前に宣言 | 同上 |
| pullの前にUnityを閉じる | Libraryフォルダの破損防止 |
| FBX/PNG/音/.blendを追加する前に §1.3 のLFSが済んでいるか確認 | 巨大ファイルが通常Gitに入ると全員のcloneが遅くなり、削除も大変 |
| 1日の終わりにpush | 進捗共有 + バックアップ |
| 2日 (48時間) 詰まったらDiscordで共有 | 1人で抱えない (TEAM_PLANの48時間ルール) |

## 4. バグ対応の流れ (fix ブランチ)

バグを見つけたときの手順。基本は §2 と同じサイクルで、**ブランチ名の頭が
`fix/` になるだけ**。ただし「どこのバグか」で入口が変わる。

### 4.1 まずIssueを立てる (原則、直す前に)
バグを見つけたら、直せるかどうかに関わらず先にIssueを立てる:
```
タイトル: [バグ] 駒が成ったときに裏面が表示されない
本文:
- 再現手順: Replayシーンでgame03.jsonlを再生 → 42手目
- 期待: と金の面が表示される
- 実際: 歩のまま表示される
- 気づいた環境: Unity 6000.3.8f1 / mainの最新
```
ラベル `ブロッカー` は「誰かの作業が止まる場合」だけ付ける。
**Issueを立てる理由**: 直している間に他の人が同じバグを二重調査するのを防ぐ +
「誰が対応中か」が見える。

### 4.2 ケース別の対応

**ケースA: 自分のまだマージしていないブランチのバグ**
→ ブランチもIssueも新しく作らない。**今のブランチでそのまま直して**
コミットに含める (例: `git commit -m "成り表示のバグ修正"`)。

**ケースB: mainに入ってしまったバグ (自分の担当範囲)**
→ §2と同じ手順で、名前だけ `fix/` にする:
```bash
git switch main && git pull
git switch -c fix/promote-display     # fix/内容 で命名
# …直す…
git add -A && git commit -m "成り駒の裏面が表示されないバグを修正 (Fixes #12)"
git push -u origin fix/promote-display
# → PRを出す。PR本文にも「Fixes #12」と書く
```
**`Fixes #12` の魔法**: PRの本文かコミットメッセージにこう書くと、
マージされた瞬間にIssue #12 が自動でクローズされる。番号はIssueのタイトル
横に出ている `#数字`。

**ケースC: 他人の担当フォルダのバグ**
→ **勝手に直さない**。Issueを立てて担当者にアサインし、Discordで一言。
理由: 相手が同じ場所を作業中かもしれず、良かれと思った修正がコンフリクトや
二重修正になる。相手が「直しておいて」と言ったら、宣言した上でケースBの
手順で直してよい (PRのレビューは担当者に依頼)。

**ケースD: 緊急バグ (統合週・デモ直前にmainが壊れた)**
→ 「mainが壊れたら全作業より優先で直す」ルールの発動:
1. Discordで「main壊れてます」と即共有 (全員のpullを止める)
2. 壊した本人 or 気づいた人が `fix/` ブランチで最短の修正
3. マージ担当 (Taka/U1) に直接連絡してPRを**最優先レビュー**してもらう
4. 直ったらDiscordで「main復旧」を流す
※ 最短の修正 = 原因コミットを打ち消すだけでもよい:
```bash
git revert <壊したコミットのID>   # そのコミットを打ち消す新コミットを作る (履歴は消さない)
```
コミットIDは `git log --oneline` で確認。`revert` は `reset` と違って
安全 (履歴を消さない) ので、緊急時はこちらを使う。

### 4.3 原因調査に便利なコマンド
```bash
git log --oneline -10 -- 対象ファイル   # そのファイルを最近いじったコミット一覧
git blame 対象ファイル                  # 各行を最後に変更したのが誰のどのコミットか
git diff main                          # 今のブランチとmainの差分を見る
```
`git blame` は「犯人捜し」ではなく「この行の意図を誰に聞けばいいか」を
調べる道具として使うこと。

### 4.4 ブランチ命名の整理

| 接頭辞 | 用途 | 例 |
|---|---|---|
| `feature/` | 新しい機能・アセットの追加 | `feature/council-ui` |
| `fix/` | バグ修正 | `fix/promote-display` |

この2つだけでよい (hotfix/ や release/ などの流儀もあるが、5人・10週では過剰)。

## 5. コマンド早見表 (チートシート)

```bash
# 状態を見る (困ったらまずこれ)
git status               # 今どのブランチで、何が変更されているか
git log --oneline -10    # 直近10コミットの履歴

# 基本サイクル
git switch main && git pull      # 最新化
git switch -c feature/xxx        # ブランチ作成
git add -A && git commit -m "…"  # 記録
git push                          # アップロード

# ブランチ操作
git branch                # 手元のブランチ一覧 (今いる場所に*)
git switch ブランチ名      # 移動

# 「やっちゃった」の取り消し (詳細は§6)
git restore ファイル名     # コミット前の変更を捨てて元に戻す
git restore --staged ファイル名  # git addを取り消す (変更自体は残る)
```

## 6. トラブル対処集 (起きてから読む)

### 6.1 コンフリクト (CONFLICT) と言われた
2人が同じファイルの同じ場所を変更した状態。落ち着けば直せる。
1. `git status` で赤くなっているファイルを開く
2. `<<<<<<<` `=======` `>>>>>>>` という印で「自分の変更」と「相手の変更」が
   並んでいるので、**正しい形に手で書き直して印を全部消す**
3. `git add -A` → `git commit` で解決完了
- どちらを残すべきか分からなければ、**相手に聞く**のが最速
- Unityのシーン/Prefabでコンフリクトした場合は自力で直そうとせず**U1を呼ぶ**

### 6.2 FBXやPNGが開けない / 中身が数行のテキストになっている
LFSのポインタファイル問題。
```bash
git lfs install
git lfs pull
```
で実体がダウンロードされる。直らなければclone し直し (§1.3→1.4)。

### 6.3 mainブランチで作業してしまった (コミット前)
```bash
git switch -c feature/xxx    # 変更ごと新ブランチに引っ越しできる
```
そのままSTEP 3から続行でOK。

### 6.4 mainブランチでコミットまでしてしまった
```bash
git switch -c feature/xxx    # コミットごと新ブランチへ
git switch main
git reset --hard origin/main # mainをGitHubの状態に戻す
```
※ `reset --hard` は取り扱い注意 (変更が消える)。不安ならDiscordで聞いてから。

### 6.5 pushが拒否された (rejected)
自分が作業中に誰かが同じブランチを更新した。
```bash
git pull --rebase
git push
```
コンフリクトが出たら §6.1 へ。

### 6.6 直前のコミットメッセージを間違えた (pushする前)
```bash
git commit --amend -m "正しいメッセージ"
```

### 6.7 変更を全部なかったことにしたい (コミット前)
```bash
git restore .        # 全ファイルを最後のコミット状態に戻す (戻せないので注意)
```

### 6.8 何が起きてるか全然分からない
壊すのが怖ければ、**今のフォルダを触らずに別の場所へclone し直す**のが
実は一番安全で速い。手元の変更が必要なら、そのファイルだけコピーして移す。
そしてDiscordで共有 (恥ずかしいことではない。全員通る道)。

## 7. やってはいけないこと

- `git push --force` (履歴を破壊する。必要な場面はこのプロジェクトにはない)
- `main` への直接コミット/push
- 巨大ファイル (動画・学習済みモデル・zipなど) のコミット
  → 動画はDiscord/ドライブ、モデルはGitHub Releasesへ
- 他人のブランチへの無断push
- `.gitignore` に入っているもの (Library/ など) を無理やり `git add -f` で追加

## 8. 最初の練習 (キックオフ後の宿題・15分)

全員、これを1周して「流れ」を体に入れる:
1. §1 の環境構築を済ませる
2. `feature/hello-自分の名前` ブランチを作る
3. `docs/hello/自分の名前.md` というファイルを作り、意気込みを1行書く
4. コミット → push → PRを出す → マージしてもらう → ブランチを消す

これが成功すれば、以降の作業はファイルの中身が変わるだけで手順は同じ。
