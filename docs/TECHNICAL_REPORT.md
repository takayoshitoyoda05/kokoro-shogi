## 1. ひとことで言うと

ふつうの将棋 AI は「盤面」を見て手を決めます。この AI は **「駒」を見ます**。

盤上と駒台にある 40 枚の駒を、それぞれ 1 人の登場人物として扱います。
どの駒にも「生き残りたい」「攻めたい」「成りたい」「守りたい」「前に出たい」「打たれたい」という
6 つの**欲求**があり、駒の種類ごとの**性格**でその欲求の重みが変わります。
それぞれの駒が「自分はこの手を指したい」と主張し、その主張を**全員でひとつの土俵に乗せて**
一番強い主張が通ります。これが指し手になります。

さらに、駒は対局中に**感情**を持ちます。仲間が取られれば動揺し、王手をかけられれば恐れます。
駒どうしには**絆**もあり、長く守り合った駒は互いを重く見るようになります。
そして駒は取られても消えません。相手の駒台に移り、**相手の駒として生まれ変わって**盤に戻ってきます。

この「駒たちの会議」で決めた手を、Unity 側では駒の光り方や動きとして表現しています。

**強さについて正直に書くと**、外部のプロ級エンジンを基準に測ったとき、この AI の勝率は
**約 23%** です (相手は探索を 1 手に制限した状態)。そして 2026 年 9 月に試した
「もっと強くする」ための施策は、**ほとんどが効きませんでした**。この文書の後半は、
その「効かなかった」の記録と、なぜ効かなかったかの診断が中心になります。

## 2. 前提知識 — ニューラルネットワークとは何か

この章は、機械学習を知らない人のための説明です。知っている人は第 3 章へ進んでください。

### 2.1 パラメータ = つまみ

ニューラルネットワークは、たくさんの**数字**を持った計算機です。この数字を**パラメータ**と
呼びます。ラジオのつまみのようなもので、つまみの位置を変えると計算結果が変わります。

この AI には **5,000,823 個** のつまみがあります。「パラメータが 500 万」と言ったら、
つまみが 500 万個あるという意味です。

### 2.2 学習 = つまみを自動で合わせる

つまみを人の手で 500 万個合わせるのは無理なので、**正解の例をたくさん見せて、
機械に自分で合わせさせます**。これが**学習**です。

将棋なら「この局面では、強い人はこの手を指した」という例を何百万個も見せます。
機械は「自分の答えと正解がどれだけ違うか」を計算し (これを**損失**と呼びます)、
損失が小さくなる方向へつまみを少しずつ動かします。これを何百万回も繰り返します。

つまみを動かす方向を計算する方法が**逆伝播** (backpropagation) で、
動かす量の基準が**学習率** (learning rate) です。学習率が大きいと一気に動き、小さいと
慎重に動きます。

学習データを最初から最後まで 1 周することを **1 エポック** (epoch) と呼びます。
この AI は 155,992 局の棋譜を 3 周して作られました (3 エポック)。

### 2.3 推論 = つまみを固定して使う

学習が終わったら、つまみを固定して使います。局面を入れると手が出てきます。
これが**推論**です。実際の対局で AI が指すのは推論です。

学習したつまみの値を保存したファイルを**チェックポイント**と呼びます。
この文書に出てくる `ppo2.pt` や `phase37_e3.pt` はチェックポイントのファイル名です。

### 2.4 過学習 = 丸暗記

学習データを何度も見せすぎると、機械は「答えを理解する」のではなく「答えを丸暗記する」ように
なります。学習データでは正解率が上がるのに、見たことのない局面では正解できません。
これを**過学習**と呼びます。

見分け方は簡単で、学習に使ったデータ (train) と、学習に使わなかった検証用データ (val) の
両方で正解率を測ります。train だけ上がって val が上がらなければ過学習です。
**この AI は今まさにこの状態です** (第 10 章)。

### 2.5 Transformer = 「注目」で情報を集める仕組み

この AI の中核は **Transformer** という種類のニューラルネットワークです。
ChatGPT などの言語 AI と同じ仕組みです。

Transformer は、入力を**トークン**という単位に分けます。言語なら単語、この AI なら**駒**です。
各トークンは数百個の数字の並び (**ベクトル**) で表されます。

Transformer の要は **attention (注目)** です。各トークンが「他のどのトークンをどれだけ見るか」を
計算し、見た相手の情報を自分に取り込みます。将棋なら「この歩は、あの飛車をよく見て、
あの香車はあまり見ない」というふうに、駒ごとに注目先が変わります。

attention を何段も重ねて (この AI は 6 段)、トークンの情報を少しずつ豊かにしていき、
最後に「どの手を指すか」を出力します。

### 2.6 確率と softmax

AI は「この手を指す」と 1 つ決めるのではなく、「この手 40%、あの手 30%、…」という**確率**を
出します。数字の列を確率に変える計算が **softmax** です。大きい数字ほど高い確率になり、
全部足すと 1 になります。

## 3. 設計の前提

### 3.1 目的

このプロジェクトの目的は二つあります。

- **(a) 探索を使わずに、将棋を指せるだけ強くすること**
- **(b) その指し手を、駒ごとの動機として説明できること**

「探索」とは、「この手を指したら相手はこう指して、そうしたら自分は…」と先を読むことです。
ふつうの将棋 AI は 1 手あたり何万〜何億局面も先読みします。この AI は**先読みを一切しません**。
局面を 1 回見て、1 回計算して、手を決めます。これを「1 手読み」「探索なし」と呼びます。

なぜ探索を使わないのか。探索は強さには効きますが、「駒たちが会議して決める」という
説明のしかたと噛み合わないからです。先読みの結果で手が決まるなら、駒の欲求や性格は飾りに
なってしまいます。この方針は 2026-09-19 に確定しました。

代わりに、**推論時に同じ計算を何回か繰り返す** (会議ループ、第 5.6 節) ことで
計算量を増やす方向を採っています。

### 3.2 設計原則: 面白さの機能を全部切っても、素の将棋 AI が残ること

感情・性格・絆といった「面白さ」の機能は、すべて**後から足せて、切っても壊れない**形で
入れてあります。具体的には、これらの機能は**最初の値がすべて 0 の足し算**として組み込まれています。

たとえば感情の影響は「駒のベクトル + 感情から計算した値」という足し算で入ります。
学習前は「感情から計算した値」が 0 なので、足しても何も変わりません。機能をオフにすると、
感情のない素の将棋 AI と**数字レベルで完全に同じ**結果が出ます。

この原則のおかげで、新しい機能を既存のチェックポイントに足しても、その瞬間に性能が落ちることは
ありません。第 9 章で「文化リーグは強さに効かなかった」「感情 GRU を動かすと弱くなった」という
結果が出ますが、それでも**素の将棋 AI の部分は無傷**です。

## 4. 局面をどう数字にするか

AI に将棋の局面を入れるには、まず局面を数字に変換する必要があります。
この変換を**トークン化**と呼びます。

### 4.1 盤ではなく駒をトークンにする

ふつうの将棋 AI は盤の 81 マスをそれぞれ数字にします (「このマスに先手の歩がいる」など)。
この AI は**駒 40 枚**をそれぞれ数字にします。40 枚とは、先手 20 枚 + 後手 20 枚の全駒です。

各駒は 4 つの整数で表されます。

| 配列 | 形 | 値の範囲 | 意味 |
|---|---|---|---|
| `species` (駒種) | 40 個 | 0〜13 | 0=歩 1=香 2=桂 3=銀 4=金 5=角 6=飛 7=玉 / 8=と 9=成香 10=成桂 11=成銀 12=馬 13=龍 |
| `position` (位置) | 40 個 | 0〜82 | 0〜80 = 盤の 81 マス、**81 = 先手の駒台、82 = 後手の駒台** |
| `owner` (持ち主) | 40 個 | 0 / 1 | 0 = 先手、1 = 後手 |
| `promoted` (成り) | 40 個 | 0 / 1 | 成っているか |
| `mask` (有効) | 40 個 | 常に 1 | 将棋では駒が盤から消えないため、常に全駒が有効 |
| `turn` (手番) | 1 個 | 0 / 1 | 今どちらの番か |

実際の平手初期局面を数字にすると、最初の 8 駒はこうなります。

```
番号  駒の ID          species     position    owner  promoted
  0   B22_gen0_0006    5 (角)      10 (2二)     1      0
  1   B88_gen0_0035    5 (角)      70 (8八)     0      0
  2   G41_gen0_0015    4 (金)      27 (4一)     1      0
  3   G49_gen0_0018    4 (金)      35 (4九)     0      0
  4   G61_gen0_0023    4 (金)      45 (6一)     1      0
  5   G69_gen0_0026    4 (金)      53 (6九)     0      0
  6   K51_gen0_0019    7 (玉)      36 (5一)     1      0
  7   K59_gen0_0022    7 (玉)      44 (5九)     0      0
  …  (40 番まで続く)
```

### 4.2 駒の ID は対局中ずっと変わらない

各駒には `P77_gen0_0029` のような **ID** が付いています。読み方は
`<駒種の文字><最初にいたマス>_gen<世代>_<連番>` です。`P77_gen0_0029` は「7七にいた歩」です。

この ID は**対局が始まってから終わるまで変わりません**。成っても、取られても、打ち直されても
同じ ID です。上の表で駒の並び順が「角、角、金、金、金、金、玉、玉…」と一見バラバラなのは、
**ID のアルファベット順** (B, G, K, L, N, P, R, S) に並べているからです。
並びが固定なので、「3 番目の駒」と言えば必ず同じ駒を指せます。

Unity に送る `piece_id` はこの ID そのものです。**ID を分解して駒種や手番を決めないでください。**
ID は「最初に何だったか」であって「今どうか」ではありません。今の駒種は `species`、
今の持ち主は `owner`、今の位置は `position` を見てください。

### 4.3 駒は取られても消えない

ここがこの AI の一番独特な点です。

角交換をした 4 手後の局面を見ると、こうなります。

```
番号  0 (角):  position 10 (2二) → 81 (先手の駒台) / owner 1 → 0    後手の角を先手が取った
番号  1 (角):  position 70 (8八) → 82 (後手の駒台) / owner 0 → 1    先手の角を後手が取った
```

取られた駒は**トークンが消えるのではなく、`position` が駒台 (81 か 82) になり、
`owner` が反転する**だけです。その後に打ち直されれば `position` が盤上のマスに戻ります。
同じトークンが、先手の駒 → 後手の持ち駒 → 後手の盤上の駒、と生き続けます。

これを「駒が敵に転生する」と呼んでいます。感情や絆も引き継がれるので、
「取られて敵になった駒が、元の仲間を攻める」といった物語が自然に生まれます。

技術的な利点もあります。**トークンの数が常に 40 で固定**されるので、
「駒が減ったら計算の形が変わる」という面倒がありません。

### 4.4 位置は「番号」でしかない

注意してほしいのは、`position` は 0〜82 の**番号にすぎない**ということです。
「5五と 5六が隣である」「飛車は同じ筋を遠くまで動ける」といった**将棋の幾何**は、
この数字には一切含まれていません。

AI は、この番号がどういう位置関係にあるかを、**500 万個のつまみを使って学習から
勝手に見つけ出しています**。これは驚くべきことですが、同時に無駄でもあります。
人間なら「隣のマス」は最初から知っているのに、AI はそれを学習しないといけないからです。
第 10 章の改良案は、ここに手を入れるものです。

### 4.5 トークンとは別に渡す 3 つの表

駒トークンとは別に、局面ごとにルールで計算して AI に渡す表が 3 つあります。

| 名前 | 形 | 値 | 何に使うか |
|---|---|---|---|
| `effect` (利き) | 40 × 40 | 0 / 1 / 2 | 駒 i から駒 j への関係。0 = 関係なし、1 = i が敵 j を取れる、2 = i が味方 j を守っている |
| `relation` (絆) | 40 × 40 | 0〜1 の実数 | 「守っている」関係を時間で積み重ねたもの (第 5.7 節) |
| `legal` (合法手) | 40 × 81 × 2 | はい/いいえ | ルール上指せる手かどうか。指せない手は候補から外す |

`effect` は「駒どうし」の関係しか表せません。「この駒は 5五の**空きマス**に利いている」
「飛車の利きはこの駒で**遮られている**」「この駒とあの駒は**3 マス離れている**」といった情報は
表せません。この制限も第 10 章で扱います。

## 5. モデルの中身

### 5.1 全体の流れ

```
局面
 ↓ トークン化 (第 4 章)
駒トークン 40 個 (各 256 個の数字)
 ↓ 共有 trunk: Transformer 6 層 (第 5.2〜5.3 節)
駒ごとの豊かな表現 40 個 (各 256 個の数字)
 ↓ 欲求・性格・自由項 (第 5.4 節)          ↓ 駒ごとの価値 V_i (第 5.5 節)
駒ごとの「この手を指したい」度合い          ↓ 単調混合
 ↓ 会議ループ R 回 (第 5.6 節)             形勢 V(s) (−1〜+1)
 ↓ 全駒まとめて softmax
指し手の確率
```

### 5.2 パラメータはどこにあるか

500 万個のつまみが、どの部品にいくつあるかの表です。

| 部品 | 役割 | パラメータ | 割合 |
|---|---|---:|---:|
| trunk (Transformer 6 層) | 駒どうしの関係を読む本体 | 4,774,176 | **95.47%** |
| proposal_embed | 会議の提案を数字にする | 108,032 | 2.16% |
| mixing | 駒ごとの価値を混ぜて形勢にする | 76,586 | 1.53% |
| desire_head | 欲求 6 軸を出す | 20,838 | 0.42% |
| free_term_head | 欲求で説明できない残り | 20,673 | 0.41% |
| personality | 駒種ごとの性格 | 518 | **0.01%** |
| **合計** | | **5,000,823** | 100% |

これとは別に、モデルの外で持っている**感情 GRU** が 4,128 個あります。

数字を見て気づいてほしいのは、**強さを担う部分 (trunk) が 95% を占め、
「こころ」に関わる部分 (性格 518 + 感情 4,128 + 絆 8) は 0.09% しかない**ことです。
第 9 章で「性格や感情をいじっても強さが変わらなかった」という結果が出ますが、
この比率を見れば当然だと分かります。

(この数字は `mood` / `relations` / `council` を有効にした構成です。`individual` と `loyalty` も
有効にすると 5,005,050 になります。)

### 5.3 共有 trunk — Transformer 6 層

trunk (幹) は、40 個の駒トークンを受け取って、駒どうしの関係を読み込み、
各駒の表現を豊かにする本体です。**同じ形の層が 6 段、直列に**並んでいます。

各駒は **256 個の数字** (256 次元のベクトル) で表されます。この 256 を **d_model** と呼びます。
6 層を通しても 256 は変わりません。

#### 1 層の中身

1 層は 789,760 パラメータで、以下の部品でできています。

```
x ← x + Attention( LayerNorm₁(x) )      ← 駒どうしを混ぜる
x ← x + FFN( LayerNorm₂(x) )            ← 1 駒の中を変換する
```

| 部品 | 中身 | パラメータ |
|---|---|---:|
| LayerNorm₁ | 256 個の数字の平均を 0、ばらつきを 1 に揃える | 512 |
| Attention | 8 ヘッド、QKV 一括 256→768、出力射影 256→256 | 263,168 |
| LayerNorm₂ | 同上 | 512 |
| FFN | 256 → 1024 → GELU → 256 | 525,568 |
| **1 層 計** | | **789,760** |

6 層 × 789,760 = 4,738,560 で、モデル全体の 94.7% です。

#### Attention — 駒どうしを混ぜる

各駒が「他のどの駒をどれだけ見るか」を計算し、見た相手の情報を自分に取り込みます。

計算の流れを説明します。各駒の 256 次元ベクトルから、3 種類のベクトルを作ります。

| 名前 | 意味 | たとえ |
|---|---|---|
| Q (Query) | 私は何を探しているか | 「自分を狙っている駒はいるか?」 |
| K (Key) | 私は何者か | 「私は敵陣にいる飛車です」 |
| V (Value) | 私が渡す中身 | 実際に取り込まれる情報 |

駒 i の Q と駒 j の K を掛け合わせた値が大きいほど「i にとって j は関係が深い」となります。
この値を softmax で確率にして、その確率で各駒の V を混ぜます。これが駒 i の新しい情報です。

**8 ヘッド**というのは、この計算を **8 通り並列に**やることです。256 次元を 32 次元ずつ 8 つに
切り分け、それぞれ独立に「誰を見るか」を計算します。1 通りだと「守りも攻めも全部混ぜた曖昧な
注目」になりますが、8 通りあれば「守りを見るヘッド」「攻めを見るヘッド」というふうに役割分担
できます。役割は人が決めるのではなく、学習で勝手に分かれます (第 5.3 節の後半で実測を示します)。

8 ヘッドの結果 (各 32 次元) を連結して 256 次元に戻し、**出力射影** (256 → 256 の行列) を通します。
出力射影は「各ヘッドが見つけたことを、256 次元のどこに書き込むか」を決める役目です。
実測では、8 ヘッドの書き込み先は互いにほぼ直交していて (ランダムな 2 本のベクトルと同程度)、
情報が上書きされずに積み上がっています。

QKV 一括 256 → 768 というのは、Q・K・V を作る 3 つの行列 (各 256 × 256) を縦に積んで
1 つの 768 × 256 行列にしているという意味です。3 回に分けて計算しても同じですが、
1 回の大きな行列積のほうが GPU では速いためです。

**32 次元というのは 256 ÷ 8 の結果**で、直接決めた数字ではありません。頭数を増やすと
1 頭あたりの次元が減り、パラメータの総数は変わりません。実測では 32 次元のうち実際に
使われているのは 6〜19 次元程度で、余裕があります (第 10.1 節)。

#### FFN — 1 駒の中を変換する

FFN (Feed-Forward Network) は、attention と違って**駒どうしを混ぜません**。
40 駒それぞれに、同じ変換を独立に適用します。

```
256 次元 → (行列 1024×256) → 1024 次元 → GELU → (行列 256×1024) → 256 次元
```

なぜ一度 1024 に広げるのか。GELU という関数が「この方向の特徴が立っているか」を判定する
ゲートの役目をするので、256 個より 1024 個のゲートがあるほうが多くのパターンを判定できる
からです。「もし〜というパターンなら〜を足す」というルールを 1024 本持てる、と考えてください。
1024 という数は 256 の 4 倍で、Transformer の慣習です。

FFN は 1 層の 66.5% のパラメータを占めます。attention より 2 倍大きいです。
言語 AI の研究では「知識は FFN に入っている」というのが現在の理解で、attention は情報を
運ぶ配線、FFN が蓄えた知識を引き出す部分、という役割分担です。

実測では 1024 個のゲートのうち死んでいる (一度も反応しない) ものはほぼ 0% で、
どれも使われています。ただし上位 10 個の寄与が 3〜4% と広く分散していて、
これは「もっと広げれば効くかもしれない」と同時に「個別の局面を丸暗記しやすい」という
過学習の温床でもあります。

#### 残差接続 — 「足す」だけで「上書き」しない

上の式で `x ← x + ...` となっているのが**残差接続**です。各層は前の x を消して作り直すのではなく、
前の x に**差分を足す**だけです。

これには 3 つの利点があります。

1. **学習の信号が消えない。** 6 層を逆向きにたどっても、「+ x」の経路が常に残ります
2. **各層が「何もしない」を選べる。** 足す量を 0 にすればいいので、6 層すべてが必ず働く必要がありません
3. **情報が積み上がる。** 実測では x の大きさが入力 14.7 → 6 層目の出口 48.3 と単調に増えていて、各層が別々の方向に書き足していることが分かります

代償として、**全 6 層で 256 次元を固定する必要**があります。足し算は同じ形どうしでないと
できないからです。モデルを太くする (256 → 384 など) と全層の形が変わり、
学習済みのつまみを引き継げなくなります。

#### LayerNorm と Pre-LN

LayerNorm は、256 個の数字の平均を 0、ばらつきを 1 に揃える処理です。
数字が層を通るうちに極端に大きくなったり小さくなったりするのを防ぎます。

この AI は **Pre-LN** という配置です。式を見ると分かるように、LayerNorm は attention や
FFN に入る**枝の側だけ**にかかり、残差の本線 (x そのもの) には触れません。
本線が最初から最後まで無加工で通るので、学習が安定します。

技術メモ: PyTorch の既製の Transformer 層 (`nn.TransformerEncoderLayer`) は使っていません。
Pre-LN の設定で**ゼロでない float マスクを渡すと出力が NaN になる**というバグがあるためです
(bool マスクと誤解釈されて全キーが塞がれる)。この AI は attention に足し算のバイアスを多用する
ので致命的で、自前実装にして回帰テスト `test_nonzero_attention_bias_stays_finite` で固定しています。

#### 直列と並列

- **6 層は直列**です。層 0 の出力が層 1 の入力になります。深くするほど時間がかかります
- **8 ヘッドは並列**です。同時に計算できます
- **40 駒トークンも並列**です。1 回の行列積でまとめて処理します

GPU が速いのは、後ろ 2 つが並列だからです。

#### 実測: ヘッドは何を見ているか

学習済みモデル (`ppo2.pt`) を開いて、8 ヘッドがどう分化したかを調べました。
次の節で説明する「利きバイアス」の学習済みの値を見ると、ヘッドごとの傾向が読めます。

| ヘッド | 「敵を取れる関係」への重み | 「味方を守る関係」への重み | 「絆」への重み | 読み取れる役割 |
|---|---:|---:|---:|---|
| head 0 | **+3.14** | +1.61 | +0.34 | 取り合いを見る |
| head 5 | +1.76 | **+2.99** | +0.02 | 守りの構造を見る |
| head 6 | **−2.06** | −1.15 | −0.10 | 利きのない駒どうしを見る |
| head 7 | −0.36 | −0.13 | **+0.82** | 長く続いた絆だけを見る |
| head 1〜4 | −1.24 〜 −0.10 | −1.71 〜 −0.35 | −0.28 〜 +0.52 | 利きを避ける / 中立 |

すべて最初は 0 だったのに、**攻撃を見るヘッド (0) と守りを見るヘッド (5) が別々に育ち**、
**利きのない駒どうしをあえて見るヘッド (6)** や**絆だけを見るヘッド (7)** も生まれています。
head 6 は無駄ではなく、「遊んでいる駒」「これから使う駒」のような、利き関係のない駒の
配置を見る役目だと考えられます。

### 5.4 attention バイアス — 将棋の知識はたった 32 個

attention の計算に、将棋のルールから来る情報を**足し算**で加えます。

```
e_ij = (Q_i · K_j) / √32  +  B_利き[ effect_ij ][ h ]  +  w_r[ h ] × r_ij
       ↑ 学習した内容から     ↑ 利きの関係 (0/1/2) に      ↑ 絆の強さに
         計算した「関係の深さ」  応じてヘッド h ごとに足す値   ヘッド h ごとの重みを掛けたもの
```

- `B_利き` は 3 行 8 列の表です。行は利きの種類 (関係なし / 敵を取れる / 味方を守る)、列はヘッド。**3 × 8 = 24 個**
- `w_r` はヘッドごとの 1 個の数字。**8 個**

**合計 32 個の数字で、将棋の駒の関係を AI に教えています。** 500 万個のうちの 32 個です。

どちらも最初は 0 です (設計原則、第 3.2 節)。つまり最初は素の attention と同じで、
学習が進むにつれて「利きがある駒は重く見る」といった傾向が育ちます。

#### 実測: 32 個はどれだけ効いているか

中盤の局面 (`lnsg1g1nl/1r1k1s3/...`) で調べました。

| | attention の「関係の深さ」のばらつき | 利きバイアスの値 | 比 |
|---|---:|---:|---:|
| head 0 | 0.684 | +3.139 | **4.59 倍** |
| head 5 | 0.834 | +1.755 | 2.10 倍 |
| head 6 | 0.606 | −2.058 | 3.39 倍 |
| head 7 | 0.902 | −0.355 | 0.39 倍 |

head 0 では、バイアス 1 個の値が、**500 万個のつまみで計算した「関係の深さ」のばらつきの
4.6 倍**もあります。ものすごく強い影響です。

ただし、利き関係がある駒のペアは 40 × 40 = 1600 ペアのうち **50 ペア (3.1%)** しかありません。
なので注目の分布が実際にどれだけ変わるかを測ると、全ヘッド平均で 5% 程度の変化にとどまります
(head 5 だけは 24% 変わる)。**32 個は「少数の重要なペアだけを、非常に強く」動かしている**
ということです。

#### この 32 個で表せないこと

| 将棋で重要な情報 | 表せるか |
|---|---|
| 駒 i が駒 j を取れる | できる |
| 駒 i が駒 j を守っている | できる |
| 空きマスへの利き (玉の逃げ道、駒を打てる場所) | **できない** (空きマスにトークンがない) |
| 飛車・角・香の線 (間に何もない直線) | **できない** |
| 遮り (間に駒が入ると利きが消える) | **できない** (結果の 0/1/2 しか見えない) |
| 距離・方向 (隣か遠いか、縦か斜めか) | **できない** |
| 何枚で守っているか | **できない** (有無だけ) |
| 層ごとの使い分け | **できない** (全 6 層で同じ 32 個を共有) |

将棋の幾何のほとんどは、この 32 個ではなく **474 万個の汎用なつまみが学習で再構成**しています。
第 10 章の改良案は、この部分に手を入れるものです。

### 5.5 方策 — 駒ごとの主張と、全員での softmax

ここからが「駒が主張する」部分です。trunk から出てきた各駒の 256 次元ベクトル h_i を使います。

#### 駒 i が手 a を指したい度合い

```
s_i(a) = ⟨w_i, d_i(a)⟩ + g_i(a)
         ↑ 性格 × 欲求      ↑ 自由項
```

- **d_i(a)**: 駒 i が手 a を指したときの**欲求 6 軸**の値。各軸は 0〜1。「この手を指すと生き残れそうか」「攻めになるか」「成れるか」「守りになるか」「前に出られるか」「打たれることになるか」
- **w_i**: 駒 i の**性格重み**。6 軸それぞれをどれだけ重視するか。**必ず正の値** (softplus という関数で保証)
- **⟨w_i, d_i(a)⟩**: 性格と欲求の掛け算の合計。「この駒の性格から見て、この手はどれだけ望ましいか」
- **g_i(a)**: **自由項**。欲求では説明できない残り。「大局観」とも言えます

性格重みが必ず正であることが、**説明可能性の要**です。負の重みがあると「生き残りたくない駒」が
生まれてしまい、読み方が分からなくなります。正なら「この駒は生存を重く見ている」と読めます。

性格重み w_i は、駒種ごとの性格 θ_sp (14 種 × 16 次元)、個体の性格 θ_ind (16 次元)、
今の感情 m_i (32 次元) を連結して 6 個の数字にし、softplus で正にしたものです。
性格に関わるパラメータは合計 **518 個**しかありません。

#### 自由項 g は「捨て駒検出器」

自由項 g には、学習中に「小さくしておけ」という罰則 (L2 正則化、係数 λ_g = 0.01) がかかります。
それでも g が大きい手があれば、それは「欲求に反してでも指すべき手」＝**捨て駒**のような
大局的判断です。λ_g を 0 から 0.01 にすると「欲求で説明できる割合」が 19% → 40% に跳ね上がり、
そのときの一致率 (正解手との一致) の低下は 0.5 ポイントだけでした。

#### 全駒まとめて 1 つの softmax

```
π(a|s) = exp(s_i,a / τ) / Σ_j Σ_a' exp(s_j,a' / τ)
```

各駒が「この手を指したい」度合い s を出したら、**40 駒 × 81 マス × 成る/成らない = 6,480 通り**
を**まとめて 1 つの softmax** にかけます。

ここが重要な設計判断です。もし駒ごとに softmax をかけると、「各駒の中での最善手」しか分かりません。
全駒をまとめることで、**「駒 A の主張が強くなれば、駒 B の確率が下がる」という競合**が
1 つの式で表現されます。これが「調停」の実体です。分母を全駒で共有しているから、
駒どうしが確率を奪い合います。

τ (温度) は分布の尖り方を決めます。τ = 0 なら最大の手を 1 つ選ぶ (argmax)。
τ が大きいほど確率が平らになり、いろいろな手を試すようになります。

ルール上指せない手は、softmax の前に −10⁹ という巨大な負の値を入れて、確率をほぼ 0 にします。

#### 計算の工夫

6,480 通りの手それぞれについて、駒のベクトル (256) と手の情報 (64) を連結した 321 次元の
入力を作ると、1 局面あたり 6480 × 321 の巨大な入力になって現実的ではありません。

そこで、第 1 層が線形 (掛け算と足し算だけ) であることを利用します。

```
W₁ × [h_i ; e_a] = W₁⁽ʰ⁾ × h_i  +  W₁⁽ᵐ⁾ × e_a
                    ↑ 駒ごと (40 回)  ↑ 手ごと (162 回)
```

駒ごとの項を 40 回、手ごとの項を 162 回だけ計算し、それを足し合わせる (ブロードキャスト) ことで、
6,480 回の計算を避けています。中間の大きさは (バッチ, 40, 162, 32) で済み、
バッチ 256 でも約 200MB です。

### 5.6 価値 — 駒ごとの価値を混ぜて形勢にする

方策 (どの手を指すか) とは別に、**価値** (今の形勢はどちらが有利か) も出します。
−1 (負け) 〜 +1 (勝ち) の数字です。

```
V(s) = tanh( Σ_i α_i × V_i + b )
```

- **V_i**: 駒 i が見た価値。各駒が 1 つずつ出します (256 → 1 の線形変換)
- **α_i**: 駒 i の**発言力**。必ず 0 以上で、全駒の合計が 1
- **b**: 全体の平均から作る補正項
- **tanh**: −1〜+1 に収める関数

α_i が 0 以上であることを**単調性**と呼びます。「駒 i の価値判断が上がれば、全体の価値も
下がらない」が保証されます (QMIX という強化学習の手法から来ています)。

この **α_i が Unity に送っている `alpha`** です。「その駒の判断が今の形勢にどれだけ効いているか」
＝発言力で、駒の光り方になります。

> **重要な事実: V_i はどの損失 (学習の目標) にも使われていません。**
> 学習では混ぜた後の V だけを「実際の勝敗」と比べます。V_i は結果的に決まるだけで、
> 直接教えられていません。ここは「局面あたり 40 個の教師をかけられる空き地」で、
> 第 10 章の次の実験はここに手を入れます。

### 5.7 会議ループ — 同じ層をもう一度通す

「会議」は、駒たちの主張を何回か往復させて手を決める仕組みです。

```
for r in 1..R:                              (R は既定で 2)
    各駒の主張 s から、上位 8 手 (駒, 手, 強さ) を選ぶ    ← これが「提案」
    提案 8 個をそれぞれ 256 次元のトークンにする        ← proposal_embed (108,032 個)
    [駒 40 個 + 提案 8 個] = 48 トークンを、
        trunk の 5 層目と 6 層目にもう一度通す          ← 新しい層は作らない
    駒トークン側の出力で、主張 s を計算し直す
```

**新しい層を作らず、既にある 5 層目と 6 層目を使い回す**のがポイントです。
だから「R を 2 から 4 に増やす」のは、学習し直さなくてもできます。
R = 2 のとき、実効的な深さは 6 層 + 2 層 × 2 = 10 層になります。

提案トークンは全駒から参照できますが、利きバイアスと絆バイアスは駒×駒の部分 (48 × 48 のうち
左上の 40 × 40) にだけ入れます。提案は駒ではないので、利きの関係を持たないからです。

会議 R = 2 で正解手との一致率は 46.16% で、会議なし (R = 0) の 28.66% から +17.5 ポイント
上がりました。ただし R = 3 以降は逆に下がります (第 9.6 節で詳しく)。

**random loop sampling** (2026-09-19 に導入): 学習時に R を {1, 2, 3, 4} からランダムに引きます。
R = 2 で固定して学習すると、推論時に R を変えたときに性能が崩れるためです。
効果は第 9.6 節に示します。

### 5.8 手をまたぐ 3 つの状態

ここまでの計算は「今の局面」だけから決まります。それとは別に、
**前の手から引き継がれる状態**が 3 つあります。

| 状態 | 大きさ | パラメータ | 更新のしかた |
|---|---|---:|---|
| 感情 m_i | 駒ごとに 32 次元 | 4,128 (全駒で共有) | 1 手ごとに 9 種類のイベントで GRU が更新 |
| 絆 r_ij | 駒のペアごとに 1 つの数字 | 8 | R ← 0.9 × R + 0.1 × (今守り合っているか) |
| 個体性格 θ_ind | 駒ごとに 16 次元 | 16 / 駒 | 対局をまたいでデータベース (SQLite) に保存 |

#### 感情 GRU

GRU (Gated Recurrent Unit) は、「前の状態」と「今の入力」から「新しい状態」を作る小さな
ニューラルネットワークです。この AI では、駒ごとに 32 次元の感情を持ち、1 手ごとに更新します。

入力は 9 種類のイベントです。

| イベント | 意味 |
|---|---|
| moved | 自分が動いた (打ちを含む) |
| captured | 自分が敵駒を取った |
| was_captured | 自分が取られて持ち駒になった |
| promoted | 自分が成った |
| ally_lost | 味方が取られた (**距離で減衰**) |
| enemy_lost | 敵駒が取られた = 味方の戦果 (**距離で減衰**) |
| threatened | 自分のマスに敵の利きが何本来ているか (0〜3 を正規化) |
| king_in_check | 自玉が王手をかけられている |
| material_swing | 駒得の増減 (自軍が得なら +、損なら −) |

`ally_lost` と `enemy_lost` は、事件が起きたマスからの距離 (L1 距離) に応じて減衰します。
**2 マス離れると 1/e (約 37%) に減ります。** 事件現場に近い駒ほど強く動揺します。

32 次元の感情から、Unity に送る 3 軸 (fear / aggression / valence) への変換は別の小さな射影で
行います (99 パラメータ)。

GRU は全駒で**同じもの**を使います (4,128 パラメータ)。ただし各駒が別々の 32 次元の状態を
持つので、駒ごとに感情は違います。

#### 絆

「駒 i が駒 j を守っている」という瞬間の関係は、利きバイアスがすでに見ています。
絆 r_ij の存在意義は、それを**時間で積み重ねる**ことです。EMA (指数移動平均) で更新し、
互いに守り合う状態が 10 手続くと約 0.65 になります。
囲いのように長く支え合った駒だけが「絆」を持ちます。

#### 個体性格

駒ごとの 16 次元の性格で、対局を跨いで蓄積されます。ただし実測では、この値の変化は
「ランダムウォーク」(でたらめに動くだけ) と区別がつかず、「経歴が性格を作る」という仮説は
現データでは支持されていません。

## 6. どうやって学習させるか

### 6.1 学習の全体像

この AI は 3 段階で学習されました。

```
① 系列蒸留 (棋譜から学ぶ)     ← 主軸。155,992 局を 3 周
② 自己対戦 PPO (自分と戦って学ぶ)  ← ①の上に 9,200 回反復
③ 文化リーグ (性格の異なる集団で競わせる)  ← ②の上に
```

結果から言うと、②と③は外部基準での強さに**ほぼ効いていません** (第 9 章)。
現在の最強モデル `ppo2` は①と②で作られたものです。

### 6.2 データ — どこから棋譜を取ってくるか

学習データは **floodgate** という将棋 AI 同士の対局サーバの棋譜です。
コンピュータ将棋の開発者が自作の AI を参加させる場所で、棋譜が公開されています。

```
floodgate の CSA ファイル
  ↓ parse_csa: 読み込む (壊れたファイルは弾く)
  ↓ accept_game: 使うかどうか判定する
  ↓ encode_game: 1 局を局面ごとに分解して数字にする
  ↓ シャード (.npz ファイル、約 10 万局面ずつ)
  ↓ SequenceDataset: 学習時に読み込む
学習
```

| 段階 | 内容 |
|---|---|
| 取得 | 年次アーカイブ (1 年 1 ファイル、約 350MB)。2026-09-21 時点で 2008〜2026 年の 19 年分 = 1,883,113 局 |
| 採否 | 両者のレート (強さの数値) が 3000 以上 / 手数が 50〜400 / 中断や不正手で終わっていない / 平手の初期局面から始まっている |
| 符号化 | 各局面をトークン 4 列 + 指された手 + 勝敗 + 欲求ラベル (次節) にする |
| 規模 | **155,992 局 ≈ 2,240 万局面** (226 シャード、11GB) |

シャードは**局の切れ目でだけ区切ります**。感情 GRU の学習には「1 局を通した流れ」が必要なので、
1 局が 2 つのファイルにまたがると困るからです。

学習時には、シャードに保存していない情報 (利き行列・合法手・イベント特徴) を、
指し手の列から局面を再生して計算し直します。保存すると容量が膨れるためです。

> **注意: 「レート 3000 以上」という条件で、全体の 53.3% の棋譜を捨てています。**
> 2026-09-21 に 6,000 局を調べて分かりました。これは第 10.2 節で見直しています。

### 6.3 欲求ラベルの自動生成 — 人手をかけずに「正解」を作る

欲求 6 軸を学習させるには、「この局面でこの駒はどんな欲求を持っていたか」という正解が必要です。
人が 2,240 万局面にラベルを付けるのは不可能なので、**棋譜からルールで自動生成**します。

「この駒はこの後どうなったか」を先読み幅 k = 4 手で見ます。

| 軸 | 判定 | 値 |
|---|---|---|
| survive (生存) | 4 手後にまだ盤上にいるか | 0 か 1 |
| attack (攻撃) | 4 手以内にこの駒が敵駒を取るか王手をかけたか | 0 か 1 |
| promote (成り) | 4 手以内にこの駒が成ったか | 0 か 1 |
| defend (守備) | 今の局面で守っている味方の数 (玉は 2 倍) を正規化 | 0〜1 の連続値 |
| advance (前進) | 4 手後に敵陣側へ進んでいるか | 0 か 1 |
| redeploy (再登場) | 持ち駒のとき、4 手以内に打たれたか | 0 か 1 |

たとえば「4 手後に取られていた駒」は survive = 0 になります。学習では、
AI が出した「この手を指すと生き残れそう」という予測 d_i と、この正解 y_i を比べます。

正解ラベルは局面 t の駒 i について 1 つで、手には依存しません。一方 AI の出力 d_i(a) は
手ごとに出ます。そこで学習では、**実際に指された手 a_t の (移動先, 成り) を全駒に当てて**
突き合わせます。

### 6.4 統一損失 — 何を目標に学習するか

損失は「AI の答えと正解の違い」を 1 つの数字にしたものです。この AI は複数の目標を
足し合わせた**統一損失**を使います。

```
L = L_policy + c₁ × L_value + c₂ × L_desire + λ_g × L_g − c₃ × H(π)
      [ + c_soft × L_teacher ]    ← エンジン教師がある局面のみ (第 9.4 節)
      [ + λ_f × L_fate ]          ← 2026-09-21 に追加、検証中 (第 10.3 節)
```

| 項 | 何を測るか | 係数 |
|---|---|---:|
| L_policy | 指された手の確率がどれだけ低いか (交差エントロピー)。強化学習では PPO 損失 | 1 (固定) |
| L_value | 形勢の予測 V と実際の勝敗 z の差の 2 乗。z は手番側から見て勝ち +1 / 引き分け 0 / 負け −1 | c₁ = 1.0 |
| L_desire | 欲求 6 軸の予測と正解ラベルの違い (BCE = 2 値の交差エントロピー) | c₂ = 0.5 |
| L_g | 自由項 g の 2 乗の平均 (合法手だけ)。「g を小さくしておけ」という罰則 | λ_g = 0.01 |
| H(π) | 確率分布の広がり (エントロピー)。強化学習でいろいろな手を試させるためのボーナス | c₃ = 0.01 |

c₃ は 2026-08-31 に 0.03 や 0.02 へ上げる実験をしましたが、どちらも「AI が覚えた知識が
壊れる」と判定されて元に戻しました。

学習中は毎エポック、**欲求説明率** = (性格 × 欲求の部分の 2 乗平均) ÷ (主張 s 全体の 2 乗平均)
を記録します。この値が大きいほど「手の選択が欲求で説明できている」、小さいほど
「自由項 (大局観) に頼っている」ことを意味します。s = ⟨w,d⟩ + g なので、g が ⟨w,d⟩ と
逆向きに動くと 100% を超えることがあります (比であって割合ではない)。

### 6.5 系列蒸留 — 主軸の学習方法

「蒸留」は、強い棋譜 (先生) から学ぶ学習法です。「系列」は、1 局面ずつではなく
**1 局を頭から終わりまで通して**学習することを指します。感情 GRU が前の手の状態を引き継ぐので、
局面をバラバラにすると感情が計算できないからです。

```
バッチ (24 局) を取り出す
    感情 m ← 0, 絆 R ← 0 に初期化
    for t in 0 .. 局の最後:                    ← 1 手ずつ、局の頭から順に
        m ← GRU(この手のイベント, m)          ← 感情を更新
        R ← 0.9 × R + 0.1 × 今の守り関係      ← 絆を更新
        出力 ← モデル(局面 t, m, R)
        損失 ← 統一損失(出力, 正解)
        損失を「窓」に積む
        16 手ごとに: 窓の損失の平均で逆伝播 → つまみを更新 → 窓を空にする → m を切り離す
```

「16 手ごとに切り離す」を **TBPTT** (Truncated Backpropagation Through Time) と呼びます。
1 局 (平均 130 手) を全部つなげて逆伝播すると計算とメモリが膨大になるので、16 手ごとに区切ります。

| 設定 | 値 | 意味 |
|---|---|---|
| 最適化アルゴリズム | AdamW | つまみの動かし方の定番手法 |
| 学習率 | 2e-4 (= 0.0002) | 1 回にどれだけ動かすか |
| 重み減衰 | 1e-2 | つまみが大きくなりすぎるのを防ぐ |
| 勾配クリップ | 1.0 | 1 回の更新量に上限をかける |
| バッチ | 24 局 | 一度に処理する局数 |
| TBPTT | 16 手 | 逆伝播を切る間隔 |
| 混合精度 | bf16 | 計算を半分の精度で速くする。損失計算は通常精度 |
| 検証 | 32 局 | 学習に使わない局で正解率を測る。常に通常精度 |
| 1 エポック | **約 13 時間** | 155,992 局を 1 周する時間 (実測 46,598 秒) |

技術メモ: 1 手ごとに GPU の計算結果を CPU に取り寄せる (`float()` を呼ぶ) と、
その待ち時間だけで CPU が 1 コア分張り付きます。そのため損失は GPU 上のテンソルのまま
足し続け、バッチの最後で 1 回だけ取り寄せます。コードで損失関数が 2 つに分かれている
(`compute_loss` と `compute_loss_tensors`) のはこのためです。

### 6.6 自己対戦 PPO — 自分と戦って学ぶ

蒸留で作ったモデル同士を戦わせ、勝った側の手を強化する学習法です。
PPO (Proximal Policy Optimization) は強化学習の定番アルゴリズムです。

強化学習では、「良い手」を直接教える代わりに、**局の最後に勝敗 (報酬) が分かる**ので、
そこから「どの手が勝ちに貢献したか」を逆算します。この AI では:

- 報酬は局の最後だけ (勝ち +1 / 負け −1 / 引き分け 0)。途中の手には報酬なし (疎報酬)
- 貢献度の計算は GAE (γ = 1, λ = 0.95)
- 将棋は手番が交互の零和ゲームなので、価値は**手番側から見た値**で持ち、次の手の値は符号を反転して伝えます (negamax 流)

```
δ_t = r_t + γ × (−V(s_{t+1})) − V(s_t)     ← 「予想より良かったか」
Â_t = δ_t + γ λ × (−Â_{t+1})                ← 貢献度を後ろから累積
```

| 設定 | 値 |
|---|---|
| 1 回の反復で集める対局 | 16 局。温度 τ = 0.8 (いろいろな手を試す)。最大 180 手 |
| 更新 | 集めたデータで 2 エポック、ミニバッチ 256、学習率 1e-5 |
| 相手 | 過去の自分のスナップショット最大 5 個から選ぶ |
| 感情 GRU | **既定で凍結** (更新しない)。感情は観測の一部として扱う |

欲求ラベルは自己対戦の棋譜からその場で生成します (蒸留と同じ規則)。
180 手で終わらなかった局は引き分け扱いです。

### 6.7 文化リーグ — 性格の違う集団で競わせる

「文化」= 駒種ごとの性格セット (θ_sp、14 種 × 16 次元 = 224 個) + 温度と λ_g の組。
複数の文化を用意し、それぞれで自己対戦 PPO を回し、総当たりで戦わせ、
負けた文化を勝った文化のコピー + ノイズで置き換えます (PBT = Population Based Training)。

trunk とヘッドは**全文化で共有**します。文化ごとに違うのは性格 224 個だけです。
**この数字が、第 9.2 節の結果を理解する鍵になります。**

```
phase37_e2 → phase37_e3 → ppo2 → いろいろな派生
  0.110         0.220      0.230     0.00〜0.245
```

すべてのモデルは `phase37_e3` (蒸留 3 エポック) を起点にしています。
数字は外部基準での勝率 (第 8 章) です。

## 7. どうやって指すか (推論)

### 7.1 持ち回る状態

この AI の推論は「局面を入れたら手が出る」という単純な関数ではありません。
**対局の始めから終わりまで、状態を持ち回ります。**

```
初期化:   感情 m ← 0, 絆 R ← 0, 駒の追跡器 (tracker) を初期局面で作る
1 手ごと: 盤を進める → tracker で駒の ID を追跡 → イベント (9 種) を計算
          → m ← GRU(イベント, m) → R ← 0.9 R + 0.1 × 守り関係 → 利き行列を計算し直す
```

`Position` というオブジェクトがこれを担当します。

> **制限: 持ち駒がある局面からは始められません。**
> 「この持ち駒の歩は、元はどの歩だったか」は盤面からは決まらないので、
> 駒の ID を復元できないからです。USI で途中の局面を指定されると、tracker を諦め、
> **感情・絆・会議の記録を持たない「記憶なし」モード**で指します (警告を出します)。
> 平手の初期局面から手順を送ってもらえれば、ふつうに動きます。

### 7.2 指し手の選択

```
1. 1 手詰みチェック (cshogi の mate_move_in_1ply) → 詰みがあればそれを指す
2. モデルを 1 回計算 → 6,480 個の数字 (主張 s)。ルール上指せない手は −10⁹
3. τ = 0 なら最大の手 (argmax)。τ > 0 なら softmax(s/τ) の確率でランダムに選ぶ
4. 選んだ番号 → (駒トークン, 移動先, 成り) → cshogi の手に変換
```

既定は **τ = 0 (常に最大の手) + 1 手詰みチェックあり**です。
1 手詰みチェックを入れているのは、探索なしのモデルは単純な詰みでも見逃すことがあるからです。

「番号 → 手」の変換は、合法手を全部走査して逆引き表を作ります。
持ち駒を打つ手は「同じ種類の持ち駒のうち ID が最小のトークン」に割り当てる、という規約です。

> **落とし穴: 常に最大の手を選ぶ AI と、決定論的なエンジンを戦わせると、同じ棋譜が量産されます。**
> 2026-09-19 の最初の測定では 50 局中 49 局が同一の棋譜になり、「勝率 0.48」という
> 間違った数字が出ました。今は floodgate から抜き出した 500 種類の序盤から開始局面を配り、
> **異なる棋譜の数を必ず一緒に報告する**ようにしています。

### 7.3 計算量

| 項目 | 値 |
|---|---|
| 1 手あたりのモデル計算 | **1 回** (先読みなし) |
| 実効的な深さ | 6 層 + 2 層 × R。既定 R = 2 で 10 層 |
| R の変更 | 学習し直さずに変えられる。R = 1〜6 を実測済み |
| 速度 | 100 局 (平均 130 手) を CPU 2 スレッドで 40〜55 秒 |

### 7.4 どこから使えるか

| 入口 | 用途 |
|---|---|
| `scripts/play_server.py` | WebSocket + JSONL。**Unity クライアント向け**。感情・欲求・会議の記録・キャリアを送る |
| `scripts/usi_server.py` | USI エンジンとして公開。将棋所などの GUI から接続できる |
| `scripts/eval_vs_engine.py` | 外部エンジンと対戦して絶対的な強さを測る (第 8.2 節) |
| `scripts/eval_vs_model.py` | 固定した過去のモデルと対戦して相対的な強さを測る (第 10.4 節) |

Unity へは schema 1.1 の JSONL を送ります。1 手ごとに 40 駒それぞれの
`mood` (fear / aggression / valence)、`desire` 6 軸、`alpha` (発言力)、`relations` と、
会議の記録 (ラウンドごとの上位提案と強さ)、自然言語の実況が含まれます。
データの形式の正本は [`docs/INTERFACE.md`](./INTERFACE.md) です。

## 8. どうやって強さを測るか

### 8.1 2026-09-19 より前の問題

それまでの「強さ」の数字は、**すべて自分の過去のモデルとの比較**でした
(対 ppo2 の勝率、はしご式の Elo、リーグ内の総当たり)。
自己対戦で勝率 71% と出ても、それは「自分の以前のバージョンより強い」という意味でしかなく、
**世の中の将棋 AI と比べてどうか**は一度も測られていませんでした。

### 8.2 外部基準の構築

2026-09-19 に、初めて外部のエンジンを固定した基準として立てました。

| 要素 | 設定 | 理由 |
|---|---|---|
| 相手 | やねうら王 9.80git + Háo (NNUE 評価関数、halfkp_256x2-32-32) | 公開されている強い将棋 AI |
| 強さの制限 | 探索を 1 手に制限 (`go depth 1`) | こちらが探索なしなので、条件を近づける |
| 序盤 | floodgate から抜き出した 500 種類。局 i は序盤 i÷2 から | 同じ棋譜の量産を防ぐ。先後で同じ序盤を 1 回ずつ |
| 局数 | 100 局 (先手 50、後手 50) | 標準誤差 (SE) ≈ 0.04 |
| 報告 | 勝率、先後別の勝率、**異なる棋譜の数** | 標本が縮退していないか確認できる |
| 比較 | **対応あり符号検定** | 同じ序盤・同じ手番なので、局ごとに「どちらが勝ったか」を比べられる |

**対応あり符号検定**とは: モデル A とモデル B を同じ 100 局面から戦わせ、
「A が勝って B が負けた局」と「B が勝って A が負けた局」を数え、
その偏りが偶然で説明できるか (p 値) を計算するものです。
p 値が 0.05 より小さければ「偶然ではなさそう」と判断します。

### 8.3 主要な結果

| モデル | 由来 | 対 Háo depth 1 |
|---|---|---:|
| teach2023_50k | エンジン教師蒸留 5 万局 | 0.245 |
| **ppo2** | phase37_e3 + PPO 9,200 反復 (**現在の最強**) | **0.230** |
| phase37_e3 | 蒸留 3 エポック (全系列の起点) | 0.220 |
| phase37_e4 | 蒸留 4 エポック | 0.200 |
| main_teacher / main_control | 教師蒸留 2 万局 / 同条件の対照 | 0.180 / 0.160 |
| phase37_e2 | 蒸留 2 エポック | 0.110 |
| E2b culture1 | 文化リーグ | 0.100 |
| e4c_iter100 | 感情 GRU 解凍 (学習率 1e-4) | 0.050 |
| b_fix_R6 | 会議 R=2 で学習して R=6 で推論 | 0.000 |

探索の深さを変えた掃引 (depth 1 / 2 / 4) でも順位はおおむね保たれました
(ppo2 は 0.230 / 0.130 / 0.030、E2b は 0.100 / 0.100 / 0.030)。
depth 1 の結論はそのまま使えます。

### 8.4 唯一の有意な成果 — random loop sampling

会議のラウンド数 R を学習時にランダムに変える手法 (第 5.7 節) の効果です。
`b_rls` (ランダム) と `b_fix` (R=2 固定) を、同じ起点・同じ条件で学習し、推論時の R を変えて測りました。

| 推論時の R | b_rls | b_fix | 対応あり検定 |
|---:|---:|---:|---|
| 1 | 0.175 | 0.080 | 18 勝 8 敗、p = 0.076 |
| 2 | 0.190 | 0.185 | 18 勝 18 敗、p = 1.00 (差なし) |
| 4 | 0.200 | 0.040 | **18 勝 2 敗、p < 0.001** |
| 6 | 0.165 | 0.000 | **18 勝 0 敗、p < 0.001** |

固定で学習した b_fix は、推論時に R を増やすと崩壊します (R = 6 で 100 局全敗)。
ランダムで学習した b_rls は R によらず 0.165〜0.200 で安定しています。

> **正確な結論は「深くしても壊れなくなった」であって「深くすると強くなる」ではありません。**
> b_rls は R を増やしても強くならず、起点の ppo2 (0.230) も超えていません。
> 頑健性 (壊れにくさ) の確保として採用します。

## 9. 何が効いて、何が効かなかったか

うまくいった結果だけでなく、うまくいかなかった結果も同じ重みで記録します。
以下はすべて外部基準 (第 8.2 節) による実測です。

### 9.1 自己対戦 PPO — +0.01

9,200 回の反復を回して、phase37_e3 の 0.220 が ppo2 の 0.230 になりました。
自分の過去との対戦では明確に強くなっていた (勝率 0.71) のに、外部基準では誤差の範囲です。

**教訓: 自己対戦の勝率は、自分の系列の中でしか意味を持ちません。**
「以前の自分に勝てるようになった」ことと「世の中の AI に勝てるようになった」ことは別です。

### 9.2 文化リーグ — −0.07〜−0.13

すべての条件で、蒸留だけのモデルより弱くなりました。
進化させているのが性格 224 個だけであることを考えれば、500 万個のモデルの強さが動かないのは
当然とも言えます。文化の分化 (性格が文化ごとに違ってくること) の研究としては続けますが、
**強さの手段としては閉じます**。

### 9.3 感情 GRU の解凍 — 動かすほど弱くなる

感情 GRU は既定で凍結 (更新しない) ですが、これを学習で動かしたらどうなるかを試しました。
学習率と「元の値から離れないようにする力 (anchor)」の 2 つを変えて、影響を分離しました。

| 条件 | GRU の学習率 | anchor | GRU がどれだけ動いたか | 対 Háo |
|---|---:|---:|---:|---:|
| ppo2 (凍結) | — | — | 0 | 0.230 |
| E4 | 1e-5 | 1.0 | 0.091 | 0.175 |
| E4c | 1e-4 | 1.0 | 0.455 | **0.050** |
| E4b | 1e-4 | 0.1 | 0.500 | 0.110 |

GRU が動いた量の **92% は学習率だけで説明でき**、anchor はほとんど効いていません。
そして **GRU を動かすほど外部強さが下がる**関係が、4 つの点で一貫しています
(0.230 → 0.175 → 0.110 → 0.050)。

設定の問題ではなく、路線そのものが有害でした。**「感情を強化学習で育てる」は閉じます。**

### 9.4 エンジン教師蒸留 — 効果を検出できず

強いエンジン (Háo) に局面ごとの「良い手の分布」と「評価値」を出してもらい、
それを追加の教師として学習させました (180 万局面)。

| 規模 | 教師あり | 対照 (教師なし、他は同条件) | 検定 |
|---|---:|---:|---|
| パイロット 4,000 局 | 0.205 | 0.205 | 完全に同じ |
| 本走 20,000 局・全 226 シャード | 0.180 | 0.160 | 13 勝 11 敗 76 分、**p = 0.84** |

規模を 5 倍にしても効果が出ませんでした。教師データ 180 万局面は、
この手法で成功した Ruoss らの研究 (150 億データ点) の **1/8,000** です。
桁を上げるには CPU で数週間とモデルの拡大が必要なので、いったん棚上げします。

### 9.5 trunk のエポック追加 — 4 回目で頭打ち

2 エポック目 (0.110) → 3 エポック目 (0.220) で勝率が倍になっていたので、
「まだ学習が足りない、もっと回せば伸びる」という仮説で 4 エポック目を回しました。

| | train 一致率 | val 一致率 | 差 | 対 Háo |
|---|---:|---:|---:|---:|
| e2 | 45.36% | 40.91% | 4.45pt | 0.110 |
| e3 | 46.61% | 41.28% | 5.33pt | 0.220 |
| e4 | 47.34% | 41.48% | **5.86pt** | 0.200 |

e3 → e4 は 19 勝 21 敗、**p = 0.875**。仮説は棄却されました。

e3 / e4 / ppo2 が 0.20〜0.23 に固まっているのに対し、e2 だけが 0.110 です。
「e3 で跳ねた」のではなく「**e2 がたまたま谷だった**」と読むのが自然です
(e1 の重みは 8 月 31 日に上書きされて失われており、確認できません)。

### 9.6 会議のラウンド数 — 深くしても強くならない

第 8.4 節のとおり、random loop sampling で「壊れなくなる」効果はありましたが、
R を増やしても勝率は 0.165〜0.200 で横ばいでした。「もっと深く考えれば強くなる」は
今の設計では成り立ちません。

### 9.7 まとめ

| 施策 | 動かしたパラメータ | 外部勝率の変化 | 判断 |
|---|---:|---:|---|
| 自己対戦 PPO 9,200 反復 | 全体 | +0.01 | 追加投資は閉じる |
| 文化リーグ | 224 | −0.07〜−0.13 | 強さ目的では閉じる |
| 感情 GRU の解凍 | 4,128 | −0.18 (用量依存) | 閉じる |
| エンジン教師蒸留 | 全体 | ±0 (p = 0.84) | 棚上げ |
| 会議 R = 1〜6 | 0 | 横ばい | 頑健性として採用 |
| trunk 4 エポック目 | 全体 | ±0 (p = 0.88) | 閉じる |

**9 月 19 日以降に試した 6 つの施策のうち、外部基準で有意に強くなったものはゼロ**です。

## 10. いま分かっていること、次にやること

### 10.1 律速はデータ量である

第 9.5 節の表が鍵です。**学習データでの一致率 (train) は毎エポック上がり続けている
(45.4 → 47.3%) のに、検証データ (val) はほぼ止まっており (40.9 → 41.5%)、
差はエポックごとに広がっている** (4.45 → 5.33 → 5.86pt)。

これは第 2.4 節で説明した**過学習**の教科書的な形です。AI は 155,992 局を丸暗記し始めていて、
新しい局面への対応力が伸びていません。

「モデルが小さいから (容量不足)」ではありません。容量が足りないなら train も頭打ちになるはず
ですが、train はまだ伸びています。したがって**モデルを大きくするのは逆効果** (丸暗記が速くなる
だけ) で、優先すべきは**データを増やすこと**です。

補強する証拠: attention の「関係の深さ」を計算する部分が、32 次元のうち実際に使っているのは
層 0 で約 6 次元、層 4 で約 17 次元にすぎません。**用意した容量を使い切っていない**、
つまり複雑な関係を学ぶだけのデータがない、と読めます。

### 10.2 実施中の対策 — データを 3 倍に

| 施策 | 内容 | 状態 (2026-09-21) |
|---|---|---|
| 年の拡大 | floodgate の 2008〜2026 年、19 年分を取得 (360,865 → **1,883,113 局**) | 完了 |
| レート線形重み | 「3000 以上だけ使う」をやめ、2000 以上を使い、レートに応じて学習の重みを 0.05〜1.0 で変える | 実装済み |
| シャード再生成 | 2015〜2026 年の 12 年分、上限 50 万局 (現行の 3.2 倍) | 生成中 |

レートの重み付けは、文献 (Li & Jiang 2026) で「弱い棋譜を捨てるより、重みを下げて残すほうが
良い」と示されている方法です。重みは w = clip((レート − 2000) ÷ 2000, 0.05, 1.0) で、
レート 4000 以上が 1.0、2000 以下が 0.05 (最強と最弱で 20 倍の差) です。

2014 年以前は floodgate が棋譜にレートを記録していない (調べたところレート既知が 0%) ので、
重み付けができず、対象から外しました。

技術メモ: 188 万件のうち 8,523 件 (0.45%) に、改行が抜けて指し手がコメント行にくっついた
壊れた棋譜があり、これを読むと将棋ライブラリ (cshogi) が**プロセスごと落ちます** (SIGSEGV)。
Python の例外処理では捕まえられないので、読む前に「消費時間の行は必ず指し手の行の直後」という
構造のチェックで弾いています。

### 10.3 次に試すこと

**(a) 駒の一生を教師にする。** 第 5.6 節で「V_i はどの損失にも使われていない」と書きました。
ここに、棋譜から無料で分かる「この駒はこの後どうなるか」を教師として与えます。

```
f_i(t) = −γ^k         k 手後に取られる (γ は 1 より少し小さい数。遠い未来ほど小さくなる)
       = +b × γ^k     k 手後に成る
       = +c × γ^(残り手数)   最後まで生き残る

L_fate = λ_f × Σ_i (V_i − f_i)²
```

局面あたり 40 個の教師が、全 2,240 万局面に付きます。教師蒸留 (第 9.4 節) が 8% の局面にしか
教師を付けられなかったのと対照的です。

さらに、**駒が取られて相手の駒台に移る瞬間に、価値は消えずに移転する**という保存則
`L_rebirth = λ_r × Σ (V_i(t+1) − κ × V_i(t−1))²` を課します。κ は駒種ごとに学習する係数です。
持ち駒の価値は将棋で最も評価が難しい量で、これを盤上の価値と学習した換算率で結びます。

これは 2026-09-21 に実装が完了し、対照実験 (教師なし / 運命のみ / 運命 + 保存則) を実行中です。

**(b) 幾何を与える。** 第 5.4 節の 32 個の利きバイアスを、「同じ筋か、同じ段か、斜めか」
「間に何枚あるか」「何マス離れているか」を表すバイアスに置き換えます。さらに先では、
81 マスそれぞれをトークンとして追加し、「駒がマスに利いている」という本来の形で利きを表します。

ただし注意点があります。チェスの研究 (Chessformer) では、**幾何を教えなくても attention のヘッドが
駒種の動き方に勝手に特化する**ことが観察されています。つまり幾何は学習で獲得できます。
焼き込むことで得られるのは「新しい能力」ではなく「その学習に使っていた容量の節約」で、
効くかどうかは賭けです。

**(c) 価値の損失を変える。** 今の価値の損失は「V と勝敗の差の 2 乗」という単純なものです。
チェスの研究 (Czech ら) では、これを「勝ち / 引き分け / 負けの 3 分類 + 残り手数の予測」に
変えるだけで +33 Elo、入力に「駒得の差」「王手をかけている駒」などの導出可能な特徴を足すと
+97 Elo、合計 +180 Elo を得ています。同じ論文で、モデルを Vision Transformer に置き換えても
+30 Elo にとどまっています。**表現と損失のほうがアーキテクチャより効く**という結果です。

### 10.4 測定の未解決問題

すべてのモデルが勝率 0.02〜0.23 の狭い範囲に固まっています。
この範囲では 100 局戦っても「勝敗が動く局」が 10〜30 局しかなく、差を検出しにくいです。
統計的に一番差が見えやすいのは勝率 0.5 付近です。

相手を弱くして 0.5 付近に合わせようと、探索のノード数を 1 まで減らしましたが、
**ノード数 1 でも depth 1 と同じ 0.230** でした。相手の強さは探索の深さではなく
評価関数 (Háo) そのもので決まっていて、探索を削っても弱くなりません。

当面は、**過去の自分のモデル (phase37_e3) を固定の相手にして相対的な差を測る**方法
(`eval_vs_model.py`) を併用して感度を確保します。絶対的な数字のまま感度を上げるには
評価関数を弱める必要があり、まだ手を付けていません。

### 10.5 方法論の教訓

3 日間で 4 回、数字を読み間違えました。同じ間違いを繰り返さないための記録です。

- **小さい勝率の差を読みすぎない。** 「勝率 0.48」は同じ棋譜の量産だった。
  「E4 がゲートを通過」は崩壊を検出しただけで有効性の証拠ではなかった。
  「teach50k 0.245」は有意ではなかった。「e2→e3 で +0.11」は 1 点追加で消えた。
  **必ず対応あり検定を通してから述べる。**
- **ゲートは崩壊を検出するが、有効性は検出しない。** 自動ゲートを通過したモデルが外部では有害だった。
- **実行中のジョブが依存するファイルを git stash しない。** 評価が無言で失敗し、原因究明に時間がかかった。
- **損失専用のパラメータをモデル本体に足さない。** 古いチェックポイントの読み込みが全部壊れる。学習ループ側で持ち、別のキーで保存する。
- **学習の起動コマンドを記録に残す。** phase37_e3 の学習率が記録されておらず、再現が不完全になった。

## 11. 用語集

| 用語 | 意味 |
|---|---|
| パラメータ | ニューラルネットワークが持つ調整可能な数字。「つまみ」。この AI は 5,000,823 個 |
| 学習 | 正解の例を見せて、パラメータを自動で合わせること |
| 推論 | 学習したパラメータを固定して使うこと。実際に指すのは推論 |
| 損失 | AI の答えと正解の違いを 1 つの数字にしたもの。学習はこれを小さくする |
| エポック | 学習データを 1 周すること |
| 過学習 | 学習データを丸暗記して、新しいデータに対応できなくなること |
| チェックポイント | 学習途中または完了時のパラメータを保存したファイル |
| ウォームスタート | 既存のチェックポイントから学習を始めること |
| トークン | Transformer が扱う単位。この AI では駒 1 枚 |
| 埋め込み | 整数 (駒種の番号など) を数百次元のベクトルに変換する表 |
| Transformer | attention を積み重ねたニューラルネットワークの型 |
| attention | 各トークンが他のどのトークンをどれだけ見るかを計算する仕組み |
| ヘッド | attention を並列に走らせる 1 系統。この AI は 8 |
| FFN | Feed-Forward Network。各トークンを独立に変換する 2 層の網 |
| 残差接続 | 層の出力を入力に足す構造。x ← x + f(x) |
| LayerNorm | 数字の平均を 0、ばらつきを 1 に揃える処理 |
| softmax | 数字の列を確率 (合計 1) に変える関数 |
| 温度 τ | softmax の尖り方。0 で最大値だけ、大きいほど平ら |
| logit | softmax に入れる前の生の数字 |
| GRU | 前の状態と今の入力から新しい状態を作る小さな網。感情に使用 |
| EMA | 指数移動平均。新しい値を少しずつ混ぜて古い値を減衰させる |
| 蒸留 | 強い棋譜 (先生) から学ぶ学習法 |
| PPO | 強化学習の定番アルゴリズム |
| GAE | 強化学習で「どの手が勝ちに貢献したか」を計算する方法 |
| TBPTT | 長い系列の逆伝播を一定の長さで切る手法 |
| QMIX | 複数エージェントの価値を単調に混ぜる強化学習の手法 |
| p 値 | その差が偶然で説明できる確率。0.05 未満なら「偶然ではなさそう」 |
| 対応あり検定 | 同じ条件で 2 つを比べ、局ごとの勝ち負けの偏りを見る検定 |
| 標準誤差 (SE) | 測定値のばらつきの目安。100 局で勝率 0.2 なら約 0.04 |
| floodgate | コンピュータ将棋の対局サーバ。棋譜が公開されている |
| CSA | 将棋の棋譜ファイルの形式 |
| USI | 将棋 AI と GUI をつなぐ標準プロトコル |
| SFEN | 将棋の局面を 1 行の文字列で表す形式 |
| NNUE | 高速に更新できるニューラルネット評価関数。やねうら王が使う |
| Elo | 対戦成績から強さを数値化する方式。差 100 で勝率約 64% |
