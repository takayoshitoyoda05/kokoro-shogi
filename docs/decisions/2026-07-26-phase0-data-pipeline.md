# 決定: Phase 0 データパイプラインの形式と、欲求ラベルの実装上の定義

- 日付: 2026-07-26
- 決めた人: Taka (A)
- 関連: `DESIGN.md` §3(1)(2)(3) / `docs/plans/PLAN_A_algorithm.md` 週2 / Phase 0 Gate

## 何を決めたか

### 1. 駒トークンは「常に40枚」で固定し、並びは piece_id 昇順にする

本将棋では取られた駒が持ち駒になるだけで盤から消えないため、トークン数は常に40。
持ち駒には専用の位置ID (81=先手の駒台 / 82=後手の駒台) を割り当てた
(`core/tokenizer.py`)。

並びを **piece_id 昇順に固定** したのは、Phase 3 の感情GRU [A] と Phase 5 の
個体性格 [B] が「同じ駒の状態を手をまたいで持ち越す」ことを前提にしているため。
盤面のマス順に並べると、駒が動くたびにトークン位置が変わって状態を追えなくなる。

### 2. 先後の視点反転はトークナイザでやらない

手番側を常に先手として学習させたい場合は、盤面のほうを `cshogi.rotate_sfen` で
反転してからトークン化する。トークナイザ内で反転すると
「トークン → SFEN の往復が元に戻る」性質が壊れ、変換の正しさを検証できなくなる。

### 3. 利きは自前で生成する

cshogi は利き (bitboard) をPythonへ公開していないため、`core/effects.py` で
駒の動きから生成した。DESIGN.md §3(2) の attention バイアス $B_{利き}$ の素材で
あると同時に、サンプルJSONLの感情ヒューリスティックにも使っている。

正しさの根拠は cshogi 自身の手生成との突き合わせ:
王手のかかっていない局面では「駒の擬似合法手の行き先」=「利き − 自駒のマス」。
ランダム対局60局・91,668駒で不一致0を確認済み (`tests/test_labels.py`)。

### 4. 欲求6軸ラベルの実装上の定義を確定した

DESIGN.md §3(3) の表は定義が一文なので、判定を次のように読んだ (先読み $k=4$):

| 軸 | 実装での判定 | 型 |
|---|---|---|
| survive | k手後に盤上にいるか | 0/1 |
| attack | k手以内にこの駒が捕獲または王手をかけたか | 0/1 |
| promote | k手以内にこの駒が成ったか | 0/1 |
| defend | 今の局面で紐を付けている味方の数 (玉は重み2) を4で正規化 | [0,1] |
| advance | k手後に敵陣側へ進んでいるか | 0/1 |
| redeploy | 持ち駒のとき、k手以内に打たれたか | 0/1 |

**survive の注意**: 取られても k手以内に打ち直されれば「t+k で盤上」なので
生存扱いになる。持ち駒 = 転生 [E] という将棋固有の性質がラベル定義に直接効く。
「取られた瞬間に survive=0」ではない。

### 5. シャード形式: 利き行列は保存せず学習時に再計算する

npz 1局面あたり:
- トークン (species/position/owner/promoted/mask) … 160 B
- 教師手を方策ヘッドの形に分解 (move_token / move_to / move_promote)
- 勝敗 z (手番側視点)
- 欲求ラベル6軸を uint8 量子化 … 240 B

合計 **約453 B/局面** (1M局面で約450MB)。
利き行列 (40×40) を保存すると1局面あたり1.6KB増えて割に合わないので、
トークンから盤面を復元して学習時に計算する。

**シャードの切れ目は必ず局の境界に置く**。局面数ちょうどで切ると1局が2つの
シャードに分かれ、Phase 3 の感情GRU [A] のように「1局を通した系列」を要する
学習でシャードを跨いだ連結が必要になる。`ShardBuilder.flush_if_full()` を
1局終わるごとに呼ぶことで、シャードの局面数は `--shard-size` ちょうどではなく
それを少し超える値になる (10万指定で実測 99,493〜100,153)。
検証: `tests/test_dataset.py::test_games_do_not_span_shards`

### 6. 棋譜フィルタ

両者レート3000以上 / 50〜400手 / 引き分けと中断 (%CHUDAN, %ILLEGAL_MOVE 等) を除外 /
平手初期局面から始まるもののみ (恒久IDを初期位置から振るため)。

2025-01-15 の1日分で 249局 → 126局 (17,529局面) が通過。

## なぜ

- トークン数固定・並び固定は、後続Phaseの機能 [A][B] を後から足せるようにするため。
  ここを緩くすると Phase 3 で全部書き直しになる。
- ラベル定義を文書に固定したのは、λ_g 掃引やアブレーションの結果を後から
  読み直すときに「どういう教師で測った数字か」が分からなくなるのを防ぐため。

## 計測 (Phase 0 Gate: 1M局面変換ベンチ)

`scripts/make_labels.py` による変換スループット:

| 対象 | 局面数 | 秒 | 局面/秒 | 1Mあたり |
|---|---|---|---|---|
| 2025-01-15 (126局) の予備計測 `--dry-run` | 17,529 | 2.2 | 7,833 | 約2.1分 (外挿) |
| **wdoor2024 (6,967局) 本計測** | **1,000,069** | **149.5** | **6,689** | **2.5分 (実測)** |

**Gate 0 達成** (2026-07-26)。1M局面の書き出しまで含めて2.5分、出力は
`data/shards/2024/` に 10シャード・**433MB** (1局面あたり実測433B。npzのzip圧縮が
効くため見積り453Bより小さい)。

```
uv run python scripts/make_labels.py --csa-dir data/floodgate/csa/2024 \
    --limit-positions 1000000 --out-dir data/shards/2024
```

律速は `core/effects.py` の利き生成 (defend ラベルで全駒の利きを取るため)。
予備計測より1割強遅いのは、書き出しと年次アーカイブ側の平均手数の差による。
1M局面が2.5分で作れるので、Phase 1 でデータ量を増やす際も前処理は律速にならない。

## 影響

- A: Phase 1 の蒸留はこのシャード形式を入力にする。方策ヘッドの教師は
  (move_token, move_to, move_promote) の3つ組。
- 他メンバー: 影響なし (Unity向けの契約 INTERFACE.md は変更していない)。
